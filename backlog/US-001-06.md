# US-001-06 — Use the verified wallet address as the Better Auth user ID

## User story

As a wallet user and application owner, I want Better Auth SIWE sign-in to resolve my verified address to exactly one user whose stored ID is that address, so that my owner identity, wallet identity and user identity remain consistent across sign-ins.

## Story map context

- Journey/activity: [wallet identity](STORY_MAP.md#wallet-identity): connect/select a wallet → review and sign SIWE → verify proof → create or resolve the canonical address user → reuse that user on subsequent sign-ins and owner actions.
- Proposed minimal slice: adapt existing SIWE sign-in and persistence end to end, including local and approved QR completion, session resolution, and application-owner isolation. Success means wallet A signs in repeatedly with exactly one persisted user `id = lowercase(A)`; wallet B resolves to its own user and cannot acquire A's owner access.
- This refines the shared authentication foundation, not the entire third-party OIDC evaluation release. New authorization/token endpoints remain in US-004/005.
- Dependencies: [US-001](US-001.md), relevant accepted [US-001-01](US-001-01.md) wallet/QR policies, current application-registration behavior and accepted Vision/Contract. No approved predecessor scope is rewritten.
- The human selected this identity slice as the next delivery after any current delivery completes, ahead of remaining application-management/OIDC work. CLI sign-in is deferred to a separate future story; no new CLI story or transport is approved here.

## Human intent and identity rules

- Latest explicit clarification: “adapt the sign-in by SIWE in better auth and userid as address, it means one owner, one wallet, one address, one user”. This establishes the requested model for shaping; it is not READY approval.
- Interpret `userid as address` as the **stored Better Auth `user.id`**, not merely a displayed alias, a separate session field, or a future OIDC claim. Canonical form follows the existing lowercase `0x` plus 40 hex-character policy.
- For the existing supported Ethereum-mainnet EOA scope, one verified address resolves to exactly one user; that user represents exactly that address. Different addresses remain different users. Do not link a second address into the first address's user, merge users by email/name/ENS, or change an established user's ID when the connected wallet changes.
- “Owner” is the application-owner role of that verified user; it does not require a second owner account. One owner may still manage multiple applications with independent OAuth client IDs under Product Contract P3.
- This is address identity, not proof of a unique real-world person or a unique wallet installation. One wallet application/person may control several addresses; WalletGate treats them as separate users. No new person-verification or one-device restriction is proposed.
- Session IDs, session secrets, wallet-association row IDs and OAuth client IDs remain distinct technical identifiers. They must not all become the public address; a public user ID is not an authentication credential.
- The human confirmed the address/user/owner interpretation above, including separate users for different addresses controlled by one person or wallet application. CLI transport, credential delivery/storage and command distribution are deferred, not included in this identity story.

## Current behavior and framework gap

- `backend/wallet-auth/auth.ts` already uses Better Auth's SIWE plugin with custom nonce/signature checks, browser-bound attempts and server-owned SIWE session provenance. This is adaptation of existing SIWE integration, not addition of an independent login method.
- The installed plugin in `node_modules/better-auth/dist/plugins/siwe/index.mjs` creates a user without supplying an address-based `id`, then creates wallet/account associations referencing `user.id`. Its response exposes `user.id` separately from `walletAddress`. Current WalletGate session responses expose the canonical address, which alone does not establish that the stored user ID equals it.
- Existing uniqueness on wallet address plus chain does not by itself enforce the full requested one-address/one-user model or prevent orphan/partial users under failed or concurrent creation.
- Official [Better Auth SIWE documentation](https://better-auth.com/docs/plugins/siwe) describes a wallet-association table referencing `user.id`; its documented configuration is not a guarantee of address-based stored IDs. Installed package behavior must govern compatibility investigation; no upgrade is assumed.
- Delivery must use supported customization/hooks/plugins/adapters where feasible, establish that the ID comes only from validated SIWE proof, and verify creation order and concurrency. Do not modify upstream internals or globally replace unrelated model IDs with addresses. If supported APIs cannot satisfy the model, report the concrete gap for human decision rather than weaken identity or proof checks.

## Proposed scope and placement

- Adapt account resolution/creation for the existing local SIWE and approved QR sign-in paths. Preserve trusted-origin and attempt binding, signed-message validation, supported chain/account/wallet policies, five-minute challenge limits, one-hour absolute sessions, explicit logout and SIWE-only provenance.
- Make persisted `user.id`, account/wallet/session user references and authenticated owner resolution agree on the same canonical address. Keep owner application records accessible only to the same verified address; application client IDs/credentials and ownership rights do not change.
- Replace legacy identity data through an explicitly invoked local development/test reset, without preserving old identity records. The reset removes all users, sessions, wallet/account associations, pending sign-in state, registered applications/client credentials and their dependent user/application records in the selected local database. Preserve source code, server configuration and unrelated data. Existing application preservation applies to ordinary sign-ins after this reset; pre-reset registrations are intentionally removed and must be registered again.
- For a fresh environment, run the explicit one-time initialization command against an empty database before starting WalletGate. Normal server startup does not create/alter tables or update an existing schema; it requires initialized storage.
- Normal startup must refuse incompatible legacy identity data with actionable guidance and must never reset it automatically. Shared/production data resets require separate explicit authorization and are outside this story. Confirmation of the shaping packet does not authorize running a reset now.
- Expose the canonical stored user ID through the existing authenticated session response as proposed `userId`, retaining existing `address`/expiry behavior. The values must agree; no raw session token is exposed. This is a proposed API detail for review, not an approved new public Better Auth route.
- Existing owners: `backend/bootstrap/database.ts` and `schema.ts` compose the initial schema, invoked by `scripts/init-database.ts`; `backend/wallet-auth/auth.ts` and `qr.ts` own authentication/identity behavior; `backend/applications/` owns owner-authorized application behavior; `backend/oidc/` retains provider configuration. Bootstrap assembles these owners, and generic infrastructure must not import wallet-domain behavior.
- No new runtime area is required for the identity slice. If useful, a real `backend/wallet-auth/identity.ts` would own canonical identity resolution; it is a proposed feature-local module, not scaffolding or a required implementation. Propose a repository reset entry under `scripts/`, with wallet-specific reset behavior owned by wallet-auth and application-specific deletion owned by applications, composed through explicit interfaces. Document actual new file placement in `docs/PROJECT_STRUCTURE.md` before delivery; generic infrastructure must remain independent of domains. This maintenance command is distinct from deferred CLI sign-in.
- Expected supporting areas: affected frontend wallet-session types/API consumption only if needed; `tests/app/auth.test.ts`, QR/application/reset integration tests, existing browser regressions, the narrow reset entry under `scripts/`, setup/reset guidance, and `work/US-001-06/` delivery artifacts. Delivery must declare narrow actual files before editing, including shared/config/test/artifact paths. Do not create a CLI directory, empty modules or delivery artifacts while shaping.
- No UI redesign is proposed. If session display/types change, apply relevant `UI_DESIGN_CONTRACT.md` address, accessibility and state guidance without expanding screens, wallets or authentication policy.

## Acceptance criteria

Human-approved criteria. Forrest explicitly approved READY and supplied the approval name and “today”; the clock confirms 2026-11-11 in Asia/Shanghai. No reset is performed by recording approval.

- AC-01: On a fresh database initialized once before server startup, successful supported SIWE authentication for address A persists exactly one Better Auth user whose primary `id` equals lowercase(A). Wallet/account associations and each resulting session reference that ID. The authenticated session response reports equal `userId` and canonical `address`; an alias field alone does not satisfy this criterion. These facts are checked against actual persisted records and server responses.
- AC-02: After logout, browser reload where applicable, server restart and later fresh valid SIWE sign-in, A resolves to the same address-based user without creating duplicates. Supported checksum/case representations resolve to that same user. Test both ordinary local verification and approved QR completion; session lifetime/provenance rules remain those already approved.
- AC-03: A and B create distinct users whose IDs equal their respective canonical addresses. Authenticating B while an A session exists cannot link B to A's user, mutate A's ID, transfer A's applications or grant B access as A. Any replacement session must be based on valid SIWE proof for its own address and cannot silently reinterpret a surviving A credential. Attempts to supply arbitrary IDs, link another wallet, or merge through placeholder email/name/ENS are rejected or unavailable through the exposed surface.
- AC-04: Overlapping valid sign-ins for A from independent attempts/connections yield at most one canonical user and one logical address association, with no orphan users, cross-address references or partial authenticated state. A losing attempt may safely fail with retry guidance; a subsequent fresh attempt resolves to the canonical user. Database failure during identity/account/session creation cannot leave records that later grant incorrect owner access. Tests exercise persistence invariants, not only mocked adapter calls.
- AC-05: Wrong/malformed address, signature, domain/URI, unsupported chain, unknown/replayed/substituted nonce, foreign browser attempt, future validity time and expired proof create no new authenticated user/session or owner access. Test just before and exactly at challenge expiry and session expiry with existing zero-skew policy; a consumed challenge cannot complete twice. Claimed address, pre-created user row or merely linked wallet is insufficient authentication proof.
- AC-06: Protected session resolution verifies that the stored user ID, referenced user, wallet binding and SIWE-authenticated session address agree. Missing, mismatched, altered, unverified or expired state is unauthenticated. Existing reload/logout semantics hold, including server-side invalidation of the selected session, no sliding renewal and no global logout of unrelated sessions. A public address used as a forged session credential never authenticates.
- AC-07: The same address-based user can own multiple independently registered applications under current rules. Repeat sign-in retains access to that owner's applications; a different address cannot list/access them. Client IDs/secrets and end-user/owner roles remain distinct. No provider/token endpoints or broader owner permissions are exposed to accommodate the identity change.
- AC-08: Normal startup refuses a missing or uninitialized database with explicit setup guidance, without creating files/tables. Once initialized, ordinary startup/restart does not change schema. It also detects incompatible legacy identity data and refuses before modifying that data, explaining the explicit local reset procedure. Starting/restarting the server never deletes existing user/application records automatically. Compatible address-based databases start normally and retain their users, sessions and registered applications subject to existing validity rules. Test incompatible, fresh and compatible database cases; no implicit schema change or reset occurs.
- AC-09: A separately invoked maintenance command requires explicit selection of the intended local development/test database and an explicit destructive-reset acknowledgement. It removes all users, sessions, wallet/account associations, pending challenges/QR approvals and registered applications/client credentials, including dependent user/application records that would otherwise remain orphaned. Source code, server configuration and unrelated data remain intact. Old credentials and pending attempts cannot authenticate/complete after reset; old clients no longer exist. After reset, fresh valid SIWE creates the required address-based user and new registrations work. Exercise reset against representative legacy and current fixtures, repeated reset, referential integrity and failure rollback; a failure leaves no partially applied reset. Isolate deletion from concurrent application writes so stale requests cannot restore removed identity/application state.
- AC-10: The reset command does not run during startup/install, does not infer its target from an implicit default, and refuses a missing target/acknowledgement or a target declared shared/production without altering its data. Shared/production reset execution and any mechanism to authorize it are outside this story. Documentation explains that local path or environment labeling alone does not prove deployment classification, so delivery must inspect the actual target before any real reset; tests use isolated disposable fixtures. Record the selected target and reset result without exposing secrets, and do not claim these controls make the command a filesystem permission boundary.
- AC-11: Setup guidance explains `user.id = canonical address`, one-address/one-user semantics, multi-application ownership, unchanged supported audience/authentication policy, and the explicit reset's deletion scope and local-only boundary. Document the explicit empty-database initialization command before first startup. State that pre-reset users/applications/credentials are lost and owners must sign in and register applications again; existing user data is not converted. No raw keys, signatures or session secrets appear in output/logs/docs. Actual stack tests prove persisted identity, reset and ownership invariants and run existing browser/QR regressions. Full `bash scripts/verify.sh` and complete diff review are required before QA_PASSED; evidence records real results and verification limits without claiming human acceptance.

- AC-12: A separately invoked `scripts/init-database.ts --database /absolute/path/to/empty.sqlite` command creates the pinned initial schema and initialization state atomically in an empty database. It requires no wallet proof or runtime secret, never upgrades existing tables, and refuses missing/invalid arguments or any existing/partial schema without changing its records/schema. After initialization, normal server startup, real SIWE sign-in, registration and restart succeed with unchanged schema and retained current users/applications. Existing tests provision fixture databases explicitly rather than relying on server startup to initialize them.

## Dependencies and risks

- Product Contract permits internal IDs but does not require random IDs. Making stored `user.id` equal the address is a stricter story requirement compatible with external address identity; it does not change public-subject policy or authorize new protocol functionality.
- Existing users can have random IDs with dependent sessions/accounts/wallet/application records. The human selected an explicit local development/test reset of those records with deletion. Do not preserve orphan clients, silently reset during startup, delete an entire database containing unrelated data, or treat this as permission for shared/production operations.
- Deletion order, dependent records, in-flight sign-in/registration and storage failure can cause partial or reappearing state. Delivery must inspect the actual schema and concurrency model, perform atomic deletion with writes excluded, and verify the complete reset scope. No legacy user/owner mapping is guessed or merged.
- Supported ID customization and transaction behavior need delivery investigation against the installed Better Auth version. Global ID generators may lack verified wallet context; using a caller-provided address or changing IDs after session issuance can violate the required trust model.
- Current SIWE session authority and browser/QR binding must remain effective; a new address-based ID does not replace proof of wallet control.
