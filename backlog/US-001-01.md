# US-001-01 — Choose a wallet or approve SIWE login by QR

## User story

As an application owner or end user, I want to choose an installed Ethereum wallet or approve a sign-in from my phone through a clear WalletGate sign-in card, so that I can authenticate with my wallet on desktop or mobile without a vendor wallet UI kit.

## Story map context

- Journey/activity: [owner and end-user wallet authentication](STORY_MAP.md#journeys-and-release-slices), following [US-001](US-001.md).
- Human-selected order: US-001 → US-001-01 → US-002 → US-003 → US-004 → US-005. This story improves the shared authentication entry point; it does not implement relying-party OIDC sign-in.
- Selected stack: **wagmi + viem + Better Auth + shadcn/ui + Tailwind**. A custom shadcn/ui wallet dialog, CSS variables/Tailwind tokens, EIP-6963 discovery, custom SIWE QR authentication, and separate connector/application-auth state replace the earlier wallet-kit approach.
- Local journey (latest user revision): choose wallet in centered card → connect → “2 Review and sign” in the same card → sign → server verifies → “3 Signed in” in the same card → reload/logout. Keep the card dimensions consistent across steps; no review/success modal or page navigation. The phone icon opens the custom “Use your phone” QR popup by latest explicit user request. Wallet-owned SDK/extension prompts remain necessary.
- Human-confirmed QR journey when Chrome has no installed wallet extension: desktop creates request → phone scans and opens WalletGate approval page in a supported wallet environment → person confirms target login and signs SIWE → server records approval → only the originating desktop completes login. The phone approves the originating desktop login; scanning a link alone is not authentication. The approved request/session policy is recorded below.
- Existing MetaMask desktop Chrome and Android in-app-browser routes remain supported. Android Chrome handoff must use a named wallet's supported mechanism; custom QR does not imply universal wallet scanner/deep-link compatibility.

## Out of scope

- Vendor wallet UI kits, WalletConnect connectors/project IDs, a generic remote-wallet RPC relay or a new proprietary wallet protocol. The custom QR flow authenticates a WalletGate session; it does not create a reusable desktop-to-phone wallet connection.
- New OAuth/OIDC endpoints, consent, client registration/management, relying-party branding or arbitrary redirects; these remain in US-002–US-005. Preserve any existing validated authorization context.
- Changing mainnet/EOA scope, canonical identity, SIWE validity or 1-hour session policy; weakening existing browser-bound local authentication; replacing Better Auth or altering accepted US-001 history.
- Smart-contract wallets, other chains, independent password/email/social/passkey auth, trading, custody and universal wallet compatibility.
- Framework migration to Next.js and adding every wallet named in the visual reference. Optional icon packages may follow existing conventions; they do not change wallet support.
- Production deployment, paid service commitments, external account creation and optional analytics. A temporary public tunnel is not automatically authorized by a need for device testing.
