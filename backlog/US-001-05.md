# US-001-05 — Put source directly under frontend and backend

## User story

As a maintainer, I want frontend and backend code directly inside their runtime directories, so that I can navigate the project without redundant src folders while retaining clear ownership and the existing runnable application.

## Story map context

- Journey/activity: [maintainer and Codex](STORY_MAP.md#maintainer-and-codex): locate code → update it within its owner → run the application and checks → review the complete migration.
- Proposed release contribution: one behavior-preserving maintenance slice from file relocation through development, production build/start and regression verification. It supports the evaluation release without adding product capabilities.
- Dependencies/order: follows [US-001-04](US-001-04.md). The human confirmed this follow-up before US-002 so registration work starts in the requested layout. This does not approve US-002.

## Proposed scope and placement

Remove only the intermediate src layer: map every tracked file frontend/src/<path> → frontend/<path> and backend/src/<path> → backend/<path>. Keep frontend/index.html in place. Preserve all subdirectory responsibilities, names, contents and runtime separation; no flattening of domain folders. Keep one root package.json/package-lock.json, shared/contracts/ as a future runtime-neutral location, root dist output and root tests.

Current ownership remains defined by [PROJECT_STRUCTURE](../docs/PROJECT_STRUCTURE.md); its adopted skeleton documents the target that was proposed before delivery. Update active ownership/configuration together with the approved source migration during delivery. Preserve US-001-04's accepted scope/history rather than rewriting it to describe this later migration.

Expected delivery areas (not a final writable-path declaration): source/destination files under frontend/ and backend/; frontend/index.html; root package/tool configuration (package.json, tsconfig.json, vite.config.ts, playwright.config.ts, components.json, and other existing configuration only if affected); actual import/path references in tests/scripts; config/project-structure.json and config/dependency-baseline.json; current structure/setup guidance; this story and work/US-001-05/ plan, scope and evidence. Enumerate exact old/new files, reasons and test/artifact paths during delivery. No dependency upgrade or lockfile regeneration is proposed.

Record a complete before/after inventory and verify source bodies remain identical except necessary import/path references. Preserve CSS, branding, icon and attribution bytes.
- AC-02: Root development, build, start, lint, typecheck, unit/integration and browser-test commands resolve the new paths. - AC-07: Keep one root dependency manifest/lockfile with the same dependency versions; do not move/delete database files, secrets, generated output or historical artifacts as part of the source move. Do not change authentication, identity, authorization, security settings, UI design or release permissions to accommodate paths.
