# US-002 — Register independent applications with a verified wallet

## User story

As an application owner, I want to register multiple applications using my verified wallet and find their configuration when I return, so that each application can integrate independently with WalletGate.

## Story map context

- Journey/activity: [owner registers applications](STORY_MAP.md#application-owner): sign in with SIWE → view my applications → register → save credentials → return to my list.
- Release contribution: persistent, independently configured clients for the later standard OIDC integration. Registration alone does not deliver working OIDC sign-in.
- Ordering/dependencies: follows US-001 and the US-001-05 layout. US-003 adds editing/disabling; US-004 delivers protocol endpoints and token issuance; US-005 verifies an independent relying party.

## Human-approved design

The human confirmed the following choices through the grilling interview, authorized draft refinement, and subsequently explicitly approved this story as READY. The decision provenance is recorded below.

- Any wallet with an existing valid SIWE-authenticated session may register; no administrator allowlist or additional signature per application. Preserve the absolute one-hour session lifetime.
- Fixed confidential server-side web client profile: authorization code, PKCE S256, `openid` only, `client_secret_basic`, no refresh tokens. Dynamic registration and other client/authentication profiles remain disabled.
- Inputs: trimmed application name, 1–100 characters; 1–10 distinct redirect URIs. Duplicate display names are allowed; client IDs distinguish applications. No logo, description, homepage or configurable scopes.
- Redirects require HTTPS on non-loopback hostnames, including local development. HTTP callbacks and loopback hostnames/addresses are rejected. Reject wildcards, fragments, embedded credentials and duplicates. Preserve approved query parameters; later authorization matches the registered URI exactly, including port and path.
- Independent generated client IDs/secrets. Display the raw secret only in the successful creation response/view; store only its hash. No later secret retrieval, rotation or persistent browser storage of the secret.
- Include registration, the creation result with accessible copy controls, and a read-only owner list. Editing/disabling stays in US-003.
- At most 20 applications per wallet and five registration attempts per wallet per minute. Every successful registration, including a lost-secret replacement, consumes the allowance. No reset, deletion or administrative bypass in this story.
- Duplicate submissions/retries create at most one application. Reconcile uncertain outcomes against the owner list; never return an already-issued secret again. A lost creation response may therefore require a replacement registration.
- If the session expires during entry, create nothing and require reauthentication. Preserve only nonsensitive form values in the current tab for retry; never carry them into another wallet's context.

## Acceptance criteria

- AC-01: Complete owner journey — From a valid SIWE session, an owner reaches the application list and registration form, registers two applications, receives distinct client IDs and independently generated secrets, and sees both registrations after logout and signing in again. IDs are neither wallet addresses nor end-user subjects. Changing form values for a subsequent registration does not change earlier configuration. Existing sign-in/logout and QR journeys remain usable.
- AC-02: Verified ownership — Registration, list and configuration reads require an unexpired session with the existing server-verified SIWE provenance. Merely connecting/linking a wallet or presenting an unproven session is insufficient. Derive the canonical owner wallet server-side; attempts to substitute another owner are rejected without creation. Reuse valid sessions without an additional signature and reject at the absolute session-expiry boundary. Browser wallet switching alone never changes server ownership.
- AC-03: Fixed profile — Each persisted client has the agreed confidential web profile, authorization-code grant, PKCE S256 requirement, `openid` scope and `client_secret_basic` method. Reject attempts to request other scopes, grants, refresh tokens, client types or authentication methods without creating a client. Exposed alternate provider registration paths cannot bypass these controls; dynamic and unauthenticated registration remain unavailable. No token/authorization endpoint is enabled merely by installing a provider integration.
- AC-04: Field validation — Trim and require a 1–100-character name and 1–10 distinct redirect URIs. Test empty/whitespace names, the name boundary and its overflow, zero/one/ten/eleven redirects, duplicate redirects, and duplicate names across independently identified applications. Reject invalid input atomically and show actionable field errors. Treat application names as untrusted text in every view.
- AC-05: Redirect validation — Accept valid HTTPS URIs on non-loopback hostnames, including development callbacks, with explicit ports permitted. Reject HTTP (including localhost, 127.0.0.1 and [::1]), HTTPS loopback hosts/addresses, unsupported schemes, wildcard hosts/paths, fragments, embedded credentials and malformed URIs. Preserve query parameters and registered path/port values without broadening the eventual exact-match policy. Test valid HTTPS cases and each rejection. Registration does not navigate to or fetch the submitted URI.
- AC-06: Credentials — Generate independent, unpredictable client credentials server-side through supported provider functionality. Persist a secret hash, never the raw secret. The successful creation result offers accessible copy controls and explains that the secret cannot be retrieved after leaving. Keep raw secrets only in temporary result memory and the intended creation response; exclude them from URLs, persistent browser storage, list/detail responses, logs, analytics and test/screenshot artifacts. Leaving the result, logout or changing owner context clears it. Refresh/revisit does not recover it; explain replacement registration if lost.
- AC-07: Isolation and read-only list — List only the authenticated wallet's applications, showing name, client ID, redirect URIs, fixed profile and creation time, with an empty state for a new owner. A second owner cannot list or read the first owner's configuration through UI or direct requests, including guessed IDs; unauthenticated reads are denied. Never expose stored hashes or secrets. No edit, disable, delete or rotate operation is available through a hidden provider endpoint. Copy accurately describes registration as preparation for later OIDC delivery, not a working or trust-verified integration.
- AC-08: Registration limits — Persistently enforce at most 20 registrations per canonical wallet, including replacement registrations; the 20th succeeds and the 21st fails without a partial client. Apply at most five registration attempts per wallet per minute, including invalid authenticated submissions. Test the rate boundary and recovery after the window, distinct-owner isolation, and concurrent requests at the application cap. Responses explain the applicable limit and retry/recovery path; the UI does not offer an unimplemented reset. The application cap survives logout/relogin and server restart. These limits are not a claim of production abuse resistance.
- AC-09: Submission integrity — Disable duplicate UI submission while pending and enforce server-side at-most-one creation for retries of the same submission, including concurrent requests. An uncertain network outcome is reconciled against persisted owner registrations before offering another creation. A duplicate response or reconciliation never reveals an already-issued secret. Validation/auth/limit/persistence failures leave no orphan client or partially persisted configuration. Test double-clicks, retries, concurrency, lost responses and rollback failures without changing unrelated applications.
- AC-10: Expiry and recovery — If a session expires before submission, reject creation and prompt for SIWE sign-in while retaining nonsensitive form values in the current tab. After successful reauthentication as the same wallet, the owner can explicitly retry; do not auto-submit. Another wallet must not inherit the form or result. Cover rejection, pending, success, network failure, expired-session and limit states with clear progress/error text and no stale success or secret disclosure.
- AC-11: UI and accessibility — Apply the existing UI design contract and semantic tokens in light/dark themes, including system-theme changes. Form labels, field errors, status announcements, copy feedback, keyboard operation and focus recovery are accessible; long names, URIs and IDs remain usable at 320 CSS px and 200% zoom without horizontal page scrolling. Verify applicable WCAG 2.2 AA contrast and reduced-motion behavior. Theme changes never resubmit registration or change authentication. No application trust endorsement or additional wallet/platform claim is introduced.
- AC-12: Supported integration and setup — Reuse supported Better Auth provider functionality and preserve the existing SIWE-only/session and HTTP security boundaries. Document compatible dependency versions, root setup/migrations and credential handling without exposing real secrets or altering existing data destructively. Keep new ownership and dependency declarations aligned with PROJECT_STRUCTURE. A provider incompatibility is a gap to resolve or report, never permission for plaintext storage, weaker wallet authorization or hand-written protocol shortcuts.
- AC-13: Reproducible verification — During approved delivery, run full `bash scripts/verify.sh` with real registration, ownership, negative/boundary/concurrency, persistence and browser checks plus existing authentication regressions, scope/dependency checks and technical review. Record actual commands, results, tested revision and redacted UI evidence in the one story evidence file. No generated evidence substitutes for execution. Local QA, hosted CI, business acceptance and release remain separate PROCESS gates.

## Out of scope

- Editing, disabling, deletion, reactivation, ownership transfer, secret retrieval/rotation, cap reset or administrative bypass.
- CLI registration or authentication; dynamic/unauthenticated registration, allowlists, public/native clients, other grants/scopes/authentication methods and refresh tokens.
- Working discovery/JWKS, authorization, consent or token endpoints, code/token lifetime choices and independent relying-party integration; those belong to US-004/005. Any internal JWT/provider setup needed for hashed credentials must not silently publish those capabilities.
- Logos/descriptions/homepages, configurable client policy, extra login methods, UI redesign or additional wallet compatibility.
- Production abuse-protection guarantees, deployment, cost/permission/host-setting changes or destructive database operations.

## Historical delivery blocker — provider redirect policy

During authorized delivery, the actual matching OAuth provider 1.7.15 rejects HTTP loopback and HTTPS loopback redirects for application_type web. The approved AC-05 requires HTTP localhost/127.0.0.1/[::1] support. A real integration test reproduces the incompatibility. Its validateRedirectUri customization affects authorization matching only and explicitly leaves registration unchanged; no supported registration override was found.

Status is BLOCKED pending a human decision: revise this story to HTTPS redirects on non-loopback hostnames (including development), or retain the local HTTP requirement and authorize further investigation of a compatible supported integration. No AC or human metadata is changed automatically; no native-client substitution, upstream patch or post-validation database rewrite is used. Partial implementation and actual checks are recorded in work/US-002/evidence.md.
