# US-001-07 — Own OAuth clients through the verified wallet user ID

## User story

As a SIWE-verified application owner, I want my applications owned by my wallet-address user ID in Better Auth, so that registration, viewing and authorization use the same persisted identity.

## Story map context

- Journey/activity: [Application owner](STORY_MAP.md#application-owner): prove wallet control → register independent clients → view only my clients → sign in again and retain ownership.
- Minimal usable slice: explicitly initialize a fresh evaluation database, sign in as wallet A, register two independent clients, and view them after reauthentication and restart; wallet B cannot access them. This refines registration, not the complete OIDC evaluation release.
- Dependencies: [US-001-06](US-001-06.md) supplies canonical wallet user IDs and verified sessions; [US-002](US-002.md) supplies registration, limits and the read-only owner list.
- Human-selected order: this ownership refinement comes before editing/disabling in [US-004](US-004.md). Existing stories retain their own approved scope and history.

## Acceptance criteria

- AC-01: Native ownership — Creating a client through the existing supported registration API with a valid SIWE owner session stores `oauthClient.userId = session.userId = user.id = verified canonical wallet address` (lowercase `0x` plus 40 hex characters), with `oauthClient.referenceId` null. Use supported Better Auth user ownership without modifying upstream internals or rewriting ownership after creation. The client retains its own unique client ID and independent configuration and credentials.
- AC-02: Persistence and multiple clients — One wallet can register two distinct clients and retrieve both through the existing list/detail interfaces after signing out, signing in again and restarting the server. Owner queries use `userId`; they do not depend on `referenceId`. Read/retry responses never reveal a previously issued plaintext secret.
- AC-03: Authorization — Another wallet's list excludes those clients, and guessed client IDs cannot disclose or modify another owner's client. Unauthenticated, expired, unproven or mismatched user/address sessions cannot create or retrieve clients. Caller-supplied ownership fields cannot override the verified session identity. Generic provider registration/management routes remain blocked, and no new edit/delete capability is exposed.
- AC-04: Per-user cap — The existing limit of 20 clients per wallet is enforced using `userId` in both registration checks and the fresh database's concurrent-insert guard. A 21st registration is refused without an orphan client, including concurrent attempts through independent database connections/processes. Another wallet has an independent allowance, and restart does not reset counts.
- AC-05: Rate and submission integrity — Preserve the existing five-attempt fixed one-minute rate window, including invalid attempts, owner isolation and boundary behavior. Preserve owner-bound request idempotency, lost-response reconciliation, atomic rollback and concurrent retry behavior: one submission creates at most one client and retries never redisclose its secret. Existing submission/rate owner values remain canonical addresses; no unrelated record renaming is required.
- AC-06: Fresh setup only — The explicit one-time initializer creates the current schema and user-owned cap guard only in an empty database. Normal startup does not create/alter tables or convert data. Incompatible previously initialized storage, including reference-owned clients or the old reference-based cap guard, is refused with clear fresh-setup guidance before user/client data is changed or a misleading empty owner list is served. The initializer continues to refuse existing/partial storage. No automatic reset, conversion, reassignment or deployed database replacement occurs.
- AC-07: Authentication and credential regressions — Preserve accepted SIWE proof/provenance checks, canonical identity, local/QR paths, native session user binding and absolute one-hour expiry. Preserve registration validation, hashed secret storage, one-time secret display and HTTP security boundaries. The existing explicitly invoked local development/test reset still handles native client-to-user foreign keys safely; this adds no new reset or user-deletion policy.
- AC-08: Owner experience — The existing registration, list, reauthentication and recovery flows remain usable with user-owned clients, including the existing keyboard/focus, status/error feedback, responsive and light/dark requirements of the UI Design Contract. No UI redesign or additional wallet/platform support is introduced.
- AC-09: Setup guidance and verification — Document the owner mapping, explicit fresh initialization and refusal of incompatible storage, without migration/conversion instructions. During approved delivery, execute integration checks against real SQLite and the supported provider, negative/boundary/concurrency cases, relevant browser owner-flow and authentication regressions, and full `bash scripts/verify.sh`. Record actual commands/results, tested revision, technical review and limitations in the single story evidence file before QA_PASSED. Draft checks alone do not establish application correctness or acceptance.

## Dependencies and risks

- The installed provider currently selects reference ownership when `clientReference` returns an address and native session-user ownership otherwise. Delivery must verify this behavior against the pinned dependency through real integration checks. Follow the Product Contract's minimum-intrusion principle.
- `oauthClient.userId` already exists as a nullable foreign key to `user.id`; this proposal needs no additional user-ID column. The current domain queries and database cap guard use `referenceId` and must change together to avoid authorization/quota gaps.
- Existing deployed reference-owned clients will not be converted or supported by this fresh-only slice. Refusing incompatible storage protects them from silent partial operation. A future production release needs a separately authorized fresh target and operational decision; shaping authorizes neither data deletion nor deployment.
- No material scope decision remains open from this interview. The human explicitly approved this story and its ACs as READY; delivery must follow PROCESS before any QA, PR/CI, acceptance or release claim.
