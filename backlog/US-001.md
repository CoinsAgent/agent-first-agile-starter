# US-001 — Sign in to WalletGate with an Ethereum wallet

## User story

As a wallet holder, I want to prove control of my Ethereum wallet and sign in to WalletGate, so that I can establish a verified identity for later application access.

This is a provisional first slice pending human approval of the Vision, Product Contract, and the scope decisions below. It establishes WalletGate sign-in only; it does not yet deliver third-party OIDC sign-in.

## Acceptance criteria

- AC-01: In a desktop browser with a supported injected Ethereum wallet, a signed-out person can start sign-in, connect an account, review a SIWE signing request, and approve it. Only successful server verification establishes an authenticated session. The signed-in page displays the verified wallet address.
- AC-02: The accepted SIWE message identifies the configured WalletGate domain and URI, the signing address, a supported chain ID, a server-issued nonce, an issued-at time, and an expiration time. The server rejects messages with an untrusted domain or URI, an unsupported chain, invalid signature, or an address different from the verified signer; rejection creates no session.
- AC-03: Each challenge expires five minutes after issuance. A challenge at or after expiration, with an issued-at time in the future, or without the required validity fields is rejected. Altering the signed times cannot extend the server-issued deadline. These durations are proposed policy pending human approval.
- AC-04: A challenge is bound to the initiating browser sign-in attempt and can establish at most one session. Unknown nonces, challenges submitted from another browser context, and replayed successful challenges are rejected. Concurrent submissions of the same challenge cannot both succeed.
- AC-05: Connecting a wallet without signing, declining connection or signing, and submitting an invalid message leave the person signed out. The page explains the outcome and permits a fresh attempt. If no supported wallet is available, it explains that a supported wallet is required.
- AC-06: Reloading the page with a valid session retains the verified identity without requiring another signature. The proposed session expires one hour after authentication, with no sliding extension; at or after expiration, protected identity access is denied and a fresh SIWE sign-in is required. The server can distinguish this session's SIWE authentication origin from merely having a wallet linked to a user record.
- AC-07: Signing out invalidates the current session. Reloading the page or reusing that session cannot regain authenticated access. Changing the connected wallet alone does not change the authenticated identity; a different identity requires a new verified sign-in.
- AC-08: Username, email, password, passkey, and external SSO cannot independently establish an end-user session. Signed-out requests cannot retrieve the authenticated identity. The sign-in flow does not assert ownership of any mailbox or unrelated service account.

## Out of scope

- OAuth/OIDC client registration, application ownership management, consent, authorization endpoints, tokens, and public OIDC subjects.
- Mobile wallet handoff, QR connection, and deep links in this first slice.
- Smart-contract wallet authentication in this proposed first slice; supported wallets are externally owned Ethereum accounts. This boundary requires explicit human approval before READY.
- Account linking, recovery, unrelated service-account bindings, agent identity, payments, and production release.

## Dependencies and risks

- Product initialization is pending: the Vision is marked DRAFT, and approval of both product documents has not been established in this session.
- Human approval is required for desktop injected-wallet/externally-owned-account scope, deferral of mobile and smart-contract wallets, and the proposed five-minute challenge and one-hour absolute session policies.
- A configured trusted origin and explicit supported chain list are required before implementation. Proposed initial chain: Ethereum mainnet (chain ID 1); authentication requires no transaction or wallet balance.
- Delivery must investigate supported Better Auth SIWE/session capabilities and use wagmi and viem as directed by the contract. Framework gaps must be reported without weakening the accepted criteria.
- This slice creates a foundation for later application management and OIDC stories. It does not establish interoperability or production readiness.
- No known conflict with the product documents if the restricted first-slice coverage is approved as sequencing rather than a change to the broader wallet/browser/mobile objective. Address canonicalization for public OIDC subjects remains an explicit decision for the later OIDC slice.
