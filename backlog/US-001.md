# US-001 — Prove wallet control and enter a session

## User story

As an application owner or end user, I want to connect my Ethereum wallet and sign a clear authentication message, so that WalletGate recognizes my verified wallet identity.

## Story map context

- Journey/activity: [owner and end-user wallet authentication](STORY_MAP.md#journeys-and-release-slices).
- Proposed release contribution: establishes the shared SIWE authentication boundary for owner management and later OIDC authorization. This story alone is not third-party application sign-in.
- Ordering/dependencies: first story; human decisions D1–D4 in the map must be resolved before READY.

## Acceptance criteria

Detailed proposals for human review. Numeric values and audience limits below use unapproved defaults from D2–D4; revise them if those decisions change.

- AC-01: On a fresh instance started using the documented local setup, an unauthenticated visitor sees ordered steps to connect a wallet, review/sign a SIWE message, and confirm authentication. A successful signature from a supported wallet produces an authenticated view displaying the verified canonical address. No transaction or payment is required.
- AC-02: The signed message binds the selected address, configured trusted domain/URI, supported chain ID, a server-issued nonce and validity times. Verification uses the configured trusted origin rather than trusting arbitrary caller-supplied domain/origin values. A valid signature for another address, domain, URI or unsupported chain produces no authenticated session.
- AC-03: A challenge is bound to the initiating browser authentication attempt, is valid for less than 5 minutes from issuance, and may succeed only once. A signature submitted at or after its deadline, replayed after success, or submitted from a different browser attempt creates no session. Concurrent submission of one challenge yields at most one success.
- AC-04: Missing/malformed message fields, missing/invalid signatures, unknown or substituted nonces, future issued-at/not-before values, and expired messages are rejected without creating a session. Message expiration cannot exceed the server's challenge deadline. Tests cover just before and exactly at each applicable validity boundary, with zero clock-skew allowance under the proposed policy.
- AC-05: Wallet connection alone does not authenticate. User rejection, cancellation or connection loss leaves the visitor unauthenticated, gives an understandable recovery action, and permits a new attempt without using an already consumed challenge. If the connected account changes before signature, the attempt must restart or verify the newly displayed account through a new challenge; it must never silently authenticate a different address from the confirmed one.
- AC-06: Equivalent letter-case forms of the same successfully verified address display and resolve to the same lowercase `0x` plus 40 hexadecimal character identity. Two distinct verified addresses remain distinct. Internal persistence IDs may exist but are not displayed as the authoritative wallet identity. Public OIDC `sub` issuance belongs to US-004.
- AC-07: A successfully authenticated session remains usable across page reloads before its absolute 1-hour deadline and is rejected at or after the deadline; activity does not extend it. Logout invalidates that session server-side, and reuse of its previous session credential fails. After logout or expiry, protected access requires fresh valid SIWE. Another concurrent browser session is unaffected by logout of this session.
- AC-08: Protected session access accepts only a session with established SIWE authentication provenance. An unverified or merely linked wallet does not confer access. Username, email, password, passkey and external SSO cannot create an independent end-user session through exposed UI or backend authentication routes. Missing, altered or expired session credentials fail protected access.
- AC-09: Sign-in, reload and logout are demonstrated on every human-selected combination in the approved desktop/mobile matrix. No-wallet, unsupported-chain and unsupported-wallet cases give actionable feedback and grant no access. A mobile wallet in-app browser is the proposed mobile scope; external browser handoff and QR connection require separate approval.
- AC-10: A developer following the documented prerequisites, configuration and startup steps can run the authentication slice and repeat the successful and rejected sign-in cases. The setup identifies the trusted origin, supported chain and session/challenge policy; it requires no committed wallet private keys or service credentials. Actual automated checks and any physical-device/manual limitations are recorded during delivery, without treating mocked wallet tests as proof of device compatibility.

## Out of scope

- Application registration/management, OAuth/OIDC authorization/token endpoints and consent.
- Independent email/password/passkey/SSO login; unrelated mailbox/service-account verification.
- Proposed first-slice exclusions pending D2: smart-contract wallets, non-mainnet chains, QR connection and external mobile-browser handoff.
- Cross-application logout, global session revocation, production deployment and production-readiness claims.
- Agent identity, communication and payments.

## Dependencies and risks

- Accepted Vision and Product Contract govern the story. D1–D4 remain unresolved; the supported wallet/browser/OS combinations must be named before READY.
- Use supported Better Auth functionality where possible, wagmi for wallet connection and viem for signature utilities. Compatibility with the ACs is unverified; do not assume library defaults satisfy SIWE-only authentication or session provenance.
- Runtime/storage implementation choices are agent-owned within the approved contract. Unavailable device access must be reported as a verification gap, not an unsupported claim of passing AC-09.
- Authentication policy changes require human review before the corresponding ACs are approved. Implementation requires real stack-specific checks through scripts/project-verify.sh.
