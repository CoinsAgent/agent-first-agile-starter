# US-003 — Sign in to applications with wallet-based OIDC and renewable tokens

## User story

As an end user, I want to sign in to an application with my wallet, explicitly approve sharing my wallet identity and optionally permit continued access, so that the application can authenticate me and renew its authorized access without repeated wallet signatures.

## Story map context

- Journey/activity: [end user arrives, consents and returns](STORY_MAP.md#end-user): application starts authorization → wallet authentication → explicit consent → code redemption → application validates identity → optional token renewal or revocation.
- Release contribution: standard third-party sign-in, discovery, public signing keys, UserInfo and client-authenticated token revocation, with independently testable renewal boundaries.
- Dependencies: US-001, US-001-06, US-001-07 and US-002. Deliver before US-004 token-based client management, then US-005's independent integration walkthrough.
- Existing registered confidential web clients supply independent credentials and exact HTTPS redirect configuration. This story extends the initial `openid` protocol profile with optional `offline_access` and refresh-token support; it does not add owner-configurable scopes or change accepted registration limits, ownership or credential disclosure rules.

## Scope and agreed policy

- Confidential server-side web clients; authorization code with PKCE S256 and `client_secret_basic`. Scope sets are `openid` or `openid offline_access`.
- Every authorization requires explicit consent. An eligible SIWE-origin session may be reused unless the request requires fresh authentication.
- A refresh-token family is one original authorization and every refresh token descended from it. Independent authorizations, even for the same wallet and client, are separate families.
- Wallet sessions authorize initial issuance. Issued access/ID/refresh tokens follow their own lifetimes and revocation rules, independently of subsequent WalletGate logout or session expiry. Applications own their local login sessions.
- Tokens issued to third-party applications grant no client-management authority; US-004 defines that separate authorization boundary.

| Item | Agreed lifetime or boundary |
|---|---|
| Pending authorization | Five minutes from request creation; login does not extend it |
| Authorization code | 60 seconds from code issuance; single-use |
| Access token | At most 15 minutes from issuance; opaque bearer token for UserInfo |
| ID token | At most 15 minutes from issuance; signed JWT |
| Refresh-token family | Seven days from original authorization; rotation never extends the deadline |
| Tokens issued within a refresh family | Expire at the earlier of issuance + 15 minutes or the original seven-day family deadline |
| Refresh rotation | Each successful use replaces the refresh token; no reuse grace window |

At an expiry deadline, the expired request/token is unusable. Existing SIWE nonce/session deadlines remain unchanged. The family deadline is anchored to the original consent authorization that produces the code, not a later refresh.

## Acceptance criteria

The human confirmed these shaping decisions and subsequently explicitly approved this story as READY. The decision and verified approval metadata are recorded below.

- AC-01: Standard application sign-in: A registered confidential web client can start an authorization-code request with `openid`, PKCE S256 and its exact registered redirect URI. The user completes existing SIWE or reuses an eligible SIWE-origin session, explicitly allows access, and the client redeems the returned code using its credentials, matching verifier and redirect. The response contains an opaque access token and signed ID token. Standard state/nonce behavior supports independent relying-party validation. Two clients receive the same canonical wallet-address `sub` while retaining distinct credentials, audiences and redirect boundaries; a second wallet has a different `sub`.
- AC-02: Consent and denial: Every authorization displays the owner-supplied application name as plain text, client ID, server-authenticated wallet and requested access, without claiming application verification. Explain wallet-address sharing and cross-application linkability. Allow and Deny are accessible, with no preselected approval. Denial issues no code/tokens and returns the appropriate protocol error only through a validated redirect. Prior consent never silently approves a subsequent request.
- AC-03: Pending requests and identity: Each authorization is bound to its initiating browser and validated request, expires after five minutes and is independent of other tabs. Expiry, denial and successful completion make that pending request unusable; duplicate approval cannot mint multiple codes. Authentication never extends its deadline or the existing SIWE nonce deadline. A session identity change, logout or expiry before approval requires authentication and renewed consent review. Wallet-extension connection/account changes cannot silently change the authenticated user or approval identity.
- AC-04: Authentication requests: Support ordinary interactive authorization, `prompt=login`, `prompt=consent`, `prompt=none` and nonnegative `max_age`. Forced or overdue authentication requires fresh SIWE; `max_age=0` forces authentication. Session reuse never bypasses required consent. Since consent is always required, `prompt=none` produces the applicable interaction error without a code. Invalid parameter combinations, expired sessions, canceled signing and interrupted continuation have defined protocol-safe outcomes. Account-selection prompts and advanced request features are deferred, with documented standards-compliant error/ignore behavior that cannot expand access or disclosure.
- AC-05: Code redemption: Codes expire at 60 seconds and require a still-valid originating SIWE session through redemption. An authenticated failed redemption may consume the code, including wrong verifier, wrong-client binding or mismatched redirect; it issues no tokens and requires a new authorization. Concurrent redemptions cannot produce two successes. A consumed-code replay is rejected and may invalidate opaque tokens previously issued from that code, without implying retraction of issued ID tokens. Invalid client authentication cannot grant tokens or ownership.
- AC-06: Tokens, subject and claims: ID-token signature, issuer, audience, expiry and supplied nonce can be independently verified. Public `sub` is exactly the verified lowercase wallet address, consistent across clients and UserInfo. Identity information is limited to this `sub`, alongside required protocol fields. No email, email verification, name, avatar, balance or unrelated account claims are disclosed, including through extra claim requests. A placeholder email remains internal. Access and ID tokens obey the agreed 15-minute maximum and, when applicable, family-deadline cap.
- AC-07: Discovery and signing keys: Publish standard discovery and public JWKS with issuer exactly `<configured trusted origin>/api/auth`; metadata, endpoints, signatures and issuer validation agree. Signing keys survive ordinary restart with the same database and server secret. Publish public keys only. Document origin/database/secret continuity requirements; key rotation or destructive data operations are not implied by this story.
- AC-08: UserInfo and wallet logout: A valid opaque bearer access token with granted `openid` returns the canonical `sub`; missing, invalid, expired or revoked tokens fail. After successful issuance, access tokens continue to work following the originating wallet session's logout or expiry until their own expiry or applicable revocation. Issued ID tokens remain independently verifiable until expiry. Wallet logout revokes that browser session and does not claim to log applications out. Tests distinguish this behavior from the valid-session requirement before code redemption.
- AC-09: Optional offline access: Issue refresh tokens only when `offline_access` is requested and explicitly consented with `openid`. Explain that the application can renew access without another wallet signature, including after WalletGate logout. A request without this grant receives no refresh token. Each family has a durable seven-day absolute deadline from original authorization, preserved across rotation and server restarts. Reaching that deadline requires fresh SIWE and consent, even if another reusable wallet session exists.
- AC-10: Refresh exchange: The owning confidential client authenticates with `client_secret_basic` and exchanges its current refresh token for a replacement refresh token, new access token and new ID token. Old refresh tokens are single-use. Refresh does not require the original wallet session to remain live. Wallet `sub`, client binding and original authentication time are preserved; token issuance time changes without claiming another wallet signature. New token expiry is capped at the original family deadline, including a refresh one minute before it. Omitted refresh scope retains the granted scope set; repeating that same set is accepted. Narrowing or expanding scopes is rejected; changing permissions requires a new authorization.
- AC-11: Rotation, reuse and isolation: One family comprises exactly one authorization's refresh lineage, not all authorizations for a client/wallet. An owning-client-authenticated submission of a recognized already-used refresh token revokes that family and all its active access tokens, even with invalid requested scopes. Unknown tokens, invalid client authentication and wrong-client requests must not revoke another family. Separate authorizations and other clients/wallets remain unaffected. Concurrent use cannot yield two successful refreshes or leave usable family tokens after reuse-triggered revocation; clients are documented to serialize refreshes, with accidental retries potentially requiring sign-in again.
- AC-12: Client-authenticated revocation: Publish a standard token-revocation endpoint requiring the owning client's credentials. Revoking its opaque access token prevents further UserInfo use. Explicit refresh-token revocation ends that original-authorization family and its active access tokens across all generations. Attempts by another client cannot revoke it; repeated/unknown-token requests follow standard non-disclosing behavior. These actions do not retract signed ID tokens or terminate application-owned sessions and do not grant client-management permissions.
- AC-13: Negative protocol and security boundaries: Unknown clients, unregistered/invalid redirects, unsupported grants/scopes, missing/incorrect PKCE, mismatched clients, invalid authentication, expired/replayed codes, expired/reused refresh tokens and unproven SIWE sessions cannot obtain unauthorized tokens. Redirect validation preserves US-002's exact registered HTTPS rules and never sends sensitive data to an untrusted redirect. Standard server-to-server form-encoded exchange/revocation works while browser consent and wallet operations retain their origin/CSRF protections. Code/token/credential values are absent from logs, analytics, error details and committed evidence. Generic client-management/DCR routes stay unavailable. US-004 adds disabling and verifies its enforcement for authorization, code redemption and refresh issuance in this existing flow.
- AC-14: UI and accessibility: Apply the UI Design Contract to application context, consent, pending, denial, expiry, reauthentication and error/retry states. Verify keyboard operation, focus, announcements, WCAG 2.2 AA contrast, light/dark themes, narrow viewports, 200% zoom and long application names/addresses. Preserve existing wallet/QR flows and distinguish wallet connection from authenticated approval. Do not add wallet/platform support beyond existing approved coverage.
- AC-15: Reproducible verification: Executable checks cover independent RP validation with two clients, code/refresh races, just-before/at/after expiry boundaries, persisted absolute deadlines and key continuity across restart, wallet logout/session expiry, family isolation, revocation across generations, claims filtering and negative cases above. Run existing wallet/QR/registration regressions and applicable browser checks. Extend local setup/integration instructions with issuer, endpoints, client authentication, scopes, lifetimes, refresh serialization and logout/revocation semantics. This is local engineering evidence, not certification or production acceptance; the complete standalone integration walkthrough remains US-005.

## Dependencies and risks

These are source-inspection findings, not passing tests or completed compatibility proof:

- The current facade hides protocol endpoints and its same-origin JSON POST restriction is incompatible with external form-encoded token exchange. Expose only the agreed endpoints with suitable per-endpoint protections.
- Native provider consent can be remembered; `openid` alone does not prevent individual email-claim requests. Explicit consent and claim filtering need supported adaptation.
- Native access-token checks/session-deletion hooks bind tokens to browser sessions. Q7 expressly requires token survival; Q12's proposed session-bound replacement was rejected. A supported extension must prove session-independent access tokens without weakening initial SIWE or token validation, including concurrent logout.
- Native refresh expiry slides with rotation; native reuse grouping can cover all authorizations for one client/user, and explicit revocation does not match the agreed family-wide semantics. Absolute deadlines, per-authorization families and atomic reuse/revocation require supported customization and restart/concurrency tests.
- Existing canonical user IDs appear compatible with the required public `sub`; this remains subject to actual RP/claim tests. Signing algorithm/metadata/key selection must agree, including existing stored keys, without exposing private keys or silently resetting data.
- Investigate these gaps during authorized delivery using supported Better Auth interfaces. Do not modify upstream internals or silently replace the human's token/session/family policy to make tests pass. An unsupported approach or a required product/security/data-policy change must be reported for human decision.
- US-004 must separately settle management-token authority, audience, scopes, lifetime and disabling effects on existing tokens. Ordinary RP tokens from this story do not imply management permission.
