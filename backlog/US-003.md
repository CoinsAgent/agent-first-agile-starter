# US-003 — Maintain and disable only my applications

## User story

As an application owner, I want to list, update and disable my applications, so that I can maintain integrations and stop new access when an application is retired.

## Story map context

- Journey/activity: [owner maintains applications](STORY_MAP.md#application-owner).
- Proposed release contribution: demonstrates ongoing owner control and isolation across applications and owners.
- Ordering/dependencies: US-002; authorization enforcement consumes disabled state in US-004.

## Acceptance criteria

Provisional outline; detail measurable boundaries and resolve policies before READY.

- AC-01: An authenticated owner lists their applications, edits an application's display name and registered redirect URIs, and sees changes persisted after a new sign-in.
- AC-02: A second owner cannot list, inspect, modify or disable the first owner's applications through either UI or direct API calls, including guessed client IDs. Unauthenticated access is denied.
- AC-03: Disabling an owned application persists its disabled state without altering another application. US-004 must reject subsequent authorization and token issuance for disabled clients.
- AC-04: Invalid configuration changes are rejected without partially overwriting the application's previous valid settings.

## Out of scope

- Proposed: deletion, reactivation, ownership transfer, credential rotation and changes to scope/policy beyond the approved initial profile.
- Retroactive invalidation of already issued tokens unless separately approved; disabling must not be presented as that guarantee.

## Dependencies and risks

- US-002; agree editable fields, disabled-client semantics, in-flight authorization handling and effects on existing tokens before READY.
- Full protocol enforcement of disable requires US-004 and must be verified there; management UI alone cannot prove it.
