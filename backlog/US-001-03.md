# US-001-03 — Verify locally and defer PR/CI until human approval

## User story

As a maintainer working with Codex, I want implementation and QA iterations to use local verification, with PR and CI starting only after I approve the finished result, so that repeated iterations consume fewer Codex tokens while preserving required checks and human control of merging.

## Story map context

- Journey/activity: [maintainer and Codex](STORY_MAP.md#maintainer-and-codex): approve story → implement and test locally → review finished result → approve PR/CI → human merges → record acceptance.
- Proposed release contribution: one complete reusable delivery workflow spanning process documentation, skills, lifecycle validation and CI event configuration. No WalletGate product behavior changes.
- Dependencies/order: builds on [US-001-02](US-001-02.md). Proposed before the layout migration, now [US-001-04](US-001-04.md). Existing one-story WIP rules apply; drafting does not authorize concurrent delivery.

## Proposed scope

Align `docs/PROCESS.md`, shaping/delivery skills, lifecycle checks and tests, CI triggers and active workflow guidance with the requested lifecycle and delayed hosted verification. Reuse existing owners in `docs/PROJECT_STRUCTURE.md`: skills own agent workflow, scripts/tests own executable lifecycle checks, and `.github/workflows/` owns CI events. Declare exact paths in the delivery plan before implementation; do not create a competing status or approval record.

## Acceptance criteria

- AC-01: The documented and executable default lifecycle is `DRAFT → READY → IN_PROGRESS → QA_PASSED → ACCEPTED`. Remove `VERIFYING` as an active supported status and transition. Ordinary failing tests remain `IN_PROGRESS` while the agent can debug them. Use `IN_PROGRESS → BLOCKED → IN_PROGRESS` only when progress cannot continue because of missing information, an unavailable dependency or a required human decision; a failed QA result or human-requested correction returns `QA_PASSED → IN_PROGRESS`, followed by the same verification rules. WIP remains limited to one story across `IN_PROGRESS`, `BLOCKED` and `QA_PASSED`. Preserve historical evidence rather than rewriting past results.
- AC-02: During development, run focused checks appropriate to the change. Before every transition to `QA_PASSED`, run the full `bash scripts/verify.sh` and complete all required local acceptance/regression checks and technical review. After these pass, the agent directly sets `status: QA_PASSED` and records actual commands, results, reviewed revision and limitations in the evidence. CI is not a prerequisite for this technical status. A failing, missing, skipped or incomplete required check cannot yield `QA_PASSED`; no dummy checks, reduced coverage or fabricated success may satisfy this gate.
- AC-03: Before explicit human approval of the finished result, implementation/QA iterations require no PR and trigger no automatic hosted CI. Local verification remains required. Workflow trigger/job configuration prevents branch pushes and other configured automatic events from starting pre-approval verification; merely updating instructions while leaving unconditional push CI enabled does not satisfy this criterion.
- AC-04: The agent presents the finished diff/demo, local verification evidence and limitations for human review at `QA_PASSED`. Once the human explicitly approves that result for PR/CI, a PR is created through the supported host route and required CI runs for its current revision. No PR is opened early to serve as a scope-approval gate. Documentation and skills distinguish story approval, approval of the finished result to start PR/CI, and completed acceptance after merge. Required host checks remain in force.
- AC-05: CI failure or a requested change prevents merge and `ACCEPTED`. Corrections return the story to `IN_PROGRESS`, repeat the necessary local checks and review, and restore `QA_PASSED` only when those checks pass. After PR publication, updated revisions receive required CI and renewed human review; approval of an earlier revision cannot replace approval/checks of changed code. Fixes within approved scope and automatic PR CI reruns need no separate permission request; renewed human review is required before merge. Run required CI when the approved PR opens and when its code changes. Remove duplicate push-triggered full verification, including a second full run on `main` solely because the PR merged, without bypassing required host checks. The agent checks CI outcomes and fixes in-scope failures, reads detailed logs when needed, and avoids continuous polling or repeated reads of unchanged logs.
- AC-06: The human merges the reviewed story PR after required CI succeeds; that merge explicitly constitutes business acceptance, with no separate acceptance request afterward. Only after the actual human merge is confirmed does the agent record the story status as `ACCEPTED` locally, with the observed human identity, acceptance date and PR/merge provenance. `QA_PASSED`, pre-merge approval, an open/closed-unmerged PR, passing CI alone, or an agent merge cannot establish completion. The agent may record the status resulting from the already-authorized human decision and confirmed merge, but must never invent human identity or approval/acceptance metadata. Keep story front matter as the single status source. Preserve the local acceptance record and include it, with its related evidence and explicitly declared paths, in the next approved PR. Do not open a dedicated acceptance-only PR or start another CI cycle solely to persist this record. Until that later PR merges, `main` retains the earlier `QA_PASSED` status. Document that lag and how a later session recovers the local record and merge provenance before evaluating WIP; do not create a competing status file or claim the previous merge already contained this update.
- AC-07: PROCESS, `deliver-story`, `shape-story`, AGENTS and active templates/setup/structure guidance consistently describe the new lifecycle, local QA gate, delayed PR/CI and human-merge completion. Update executable lifecycle validation and relevant regression tests alongside CI configuration. Preserve unrelated approvals, application behavior and historical test/CI claims; label historical references where needed.
- AC-08: `bash scripts/verify.sh` executes real harness and application checks successfully. Relevant tests cover rejection of `VERIFYING`, WIP enforcement without that state, required local evidence, and failure/boundary cases. Validate the workflow event/job matrix for pre-approval pushes, approved PR creation/code updates and post-merge pushes without duplicate verification, and review the full declared diff. Record actual local results and hosted verification limits; local configuration tests cannot prove hosted CI ran or that a merge occurred.
