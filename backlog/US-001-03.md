# US-001-03 — Make frontend and backend ownership visible in the directory layout

## User story

As a maintainer working with Codex, I want the React frontend and Node.js backend in explicitly named directories with feature-owned code kept together, so that I can identify where code belongs without confusing frontend source with the entire application's source.

## Story map context

- Journey/activity: [maintainer and Codex](STORY_MAP.md#maintainer-and-codex): understand intended structure → propose migration paths → relocate source and update tooling → verify the unchanged application.
- Proposed release contribution: one separately reviewable migration that leaves the existing wallet sign-in application runnable and its ownership rules usable. This is maintainability work supporting the evaluation release, not a new product feature.
- Dependencies/order: [US-001-02](US-001-02.md) supplies the scope/dependency conventions and controls. Resolve its delivery gate before starting this story; the current WIP limit remains in force. Suggested next maintainer slice after that gate, before further product expansion; the human owns priority.
- The suffix does not inherit approval. Selecting directory names and requesting a separate migration does not approve these detailed ACs or authorize migration implementation. Branch paths will be proposed under PROCESS after story approval.

## Proposed minimal release and scope

Move the current frontend to `frontend/src/`, backend to `backend/src/`, and frontend HTML entry to `frontend/index.html`. Keep one root `package.json`, one root lockfile, shared root tooling and the existing central test locations. The root `shared/contracts/` remains reserved for genuinely needed safe cross-runtime contracts; do not create it without actual work requiring files there.

The selected backend uses `bootstrap/`, `wallet-auth/`, `oidc/`, `applications/` and `infrastructure/` directly under `backend/src/`; avoid generic backend `app/` or `features/` containers. Bootstrap means composition, the three named domains retain feature ownership, and infrastructure retains the existing shared-code independence rule. OIDC and application-management directories remain future destinations until their own approved stories need real files.

The selected frontend uses `bootstrap/` and `pages/` for composition, `wallet-auth/`, `authorization/` and `applications/` for named domains, and `ui/`, `lib/`, `assets/`, `styles/` for generic presentation/helpers and assets. Avoid generic frontend `app/` and `features/` containers. Consent and owner-management UI remain future work; OIDC Discovery needs no frontend page.

Group existing feature-specific modules through file placement, retaining their implementation and existing exports. Only mechanical mounting/page/bootstrap module extraction needed to realize the selected responsibilities is in scope; preserve existing component state ownership, effects and initialization order. Do not combine migration with controller rewrites, new domain public API design, feature implementation, app-state redesign, a new router library or new navigation behavior. The structure guide owns the current/target mapping; this story proposes the migration outcome and its verification, not another authoritative directory tree.

Proposed placement mapping for review:

| Existing owner | Proposed destination |
|---|---|
| `src/main.tsx` | Thin `frontend/src/main.tsx` mounting entry; existing sign-in assembly in `frontend/src/pages/sign-in.tsx`, with existing provider/page-dispatch assembly under `frontend/src/bootstrap/` as needed; preserve component logic and initialization order |
| `src/components/wallet/` | `frontend/src/wallet-auth/components/` |
| `src/hooks/use-wallet-auth.ts` | `frontend/src/wallet-auth/hooks/use-wallet-auth.ts` |
| `src/wallet.ts`, `src/wallet-sdk.ts`, `src/lib/api.ts` | `frontend/src/wallet-auth/wallet.ts`, `frontend/src/wallet-auth/wallet-sdk.ts`, `frontend/src/wallet-auth/api.ts` respectively |
| `src/components/ui/`, `src/lib/utils.ts` | `frontend/src/ui/` and `frontend/src/lib/utils.ts` |
| `src/style.css` | `frontend/src/styles/style.css`; preserve theme tokens and style behavior |
| `src/assets/`, `src/walletgate.png` | `frontend/src/assets/` and `frontend/src/assets/walletgate.png`; preserve bytes and attribution, including the original PNG |
| `server/index.ts` | `backend/src/bootstrap/server.ts`; a minimal `backend/src/index.ts` entry starts/imports that bootstrap without changing behavior |
| `server/auth.ts`, `server/qr.ts` | `backend/src/wallet-auth/auth.ts` and `backend/src/wallet-auth/qr.ts`; preserve existing auth configuration/behavior together rather than introducing a new refactor |
| `server/config.ts` | `backend/src/infrastructure/config.ts` |
| Root frontend `index.html` | `frontend/index.html` |
| Root package/tool configuration and `tests/` | Stay in place; update only affected paths/settings |

Final exact filenames, both endpoints of every move and required tooling/documentation files belong in the execution plan for human approval before implementation. No production `app/` or `features/` containers are part of the selected target. Every new directory must have a stated responsibility and owner; do not create empty domain, generic-code or package directories just to match an example skeleton. Existing central `tests/app/` retains its dedicated application unit/integration test meaning and is not a production composition folder.

## Acceptance criteria

- AC-01: Before migration edits, the human can review a complete existing→target source/entry/asset mapping, the intended skeleton, affected imports/configuration/tests/docs, and both endpoints of each move in the task scope proposal. Runtime data, credentials, dependencies, generated output and unrelated working-tree files are excluded. Adding a previously unidentified path requires explicit scope expansion.
- AC-02: After migration, the existing React source is under `frontend/src/`, Node.js backend under `backend/src/`, and HTML entry under `frontend/`. Existing wallet-specific modules are grouped by their owning feature and generic UI/helpers are identified as shared. There is no duplicate active application implementation left under root `src/` or `server/`, and no empty roadmap scaffolding. One root package/lockfile remains authoritative; there are no new workspaces or per-side package manifests.
- AC-03: From the repository root, documented install/build/start and browser-test commands still work with the same supported versions, environment variable names, origin/port policies, runtime database location and existing static-output/CSP behavior. Update Vite root/entry/output, TypeScript includes/aliases, package script paths, shadcn/Tailwind source discovery, test imports/server startup and SDK-style-hash handling as necessary. Missing files, unresolved imports, CSS/assets or a working-directory-dependent startup failure cannot be accepted as a migration success. Dependency versions/integrity and the existing security checks are preserved.
- AC-04: Existing connection, explicit SIWE review/signing, QR approval/completion, verified session/reload/logout and failure/recovery tests pass using the migrated source. The migration adds no new authentication path or wallet support and does not alter nonce/session expiry, origin binding, replay protection, canonical identity or approved protocol policy. Simulated provider/relay results remain distinguished from physical-device verification; existing deferred compatibility limitations remain documented.
- AC-05: Existing light/dark presentation, keyboard/focus behavior, responsive layout and asset availability pass their current UI regression checks. UI markup/style/state logic is preserved apart from necessary path changes; the original branding PNG and icon attribution remain present with unchanged content. A path-only migration does not authorize visual redesign or changing approved interactions.
- AC-06: Executable ownership/source roots/aliases/public-interface paths and scope controls reflect the migrated layout. Baseline entries change only to represent the same existing importer/target/rule relationships at their new paths, with reviewable old→new provenance. No wildcard exemption, new reverse dependency, broadened baseline, lowered check, or accidental browser import of backend code is introduced. Relevant negative fixtures continue to fail as expected under the new configuration; example fixtures using other directory names need not be renamed to resemble production.
- AC-07: The single structure guide clearly distinguishes actual adopted paths from any still-proposed destinations after migration. Active Codex instructions, development setup, tooling/asset references and relevant UI guidance lead to existing current paths. Preserve historical story/approval/evidence records and original results; identify old historical paths as historical rather than rewriting past evidence or acceptance. No new competing lifecycle or approval record is created.
- AC-08: `bash scripts/verify.sh` runs the actual harness/dependency checks and unchanged application regression suites successfully, without skipping failing tests. Check the complete migration diff against approved source/destination paths; inspect tracked source inventory and migrated import resolution to ensure no duplicate old application remains. Evidence records exact commands, results, base/head, baseline translations, asset preservation checks, review findings and any CI/host limitations. Follow PROCESS's branch proposal, checks and finished-change review rules; do not infer protected merging or acceptance from local tests.
- AC-09: The migrated backend distinguishes startup/composition in `bootstrap/`, existing wallet behavior in `wallet-auth/`, and generic technical code in `infrastructure/`, directly under `backend/src/`. The thin index entry preserves startup order. Executable declarations classify these as app, feature and shared roles without relying on generic container names; infrastructure-to-domain/bootstrap imports and browser-to-backend imports still fail. `oidc/` and `applications/` are documented future domains only: the migration introduces no empty modules, new protocol endpoints, handwritten token/crypto implementation, or splitting of existing auth logic simply to fit proposed filenames. OIDC Core/Discovery terminology guides future ownership; it does not prescribe filesystem or URL names.
- AC-10: The migrated frontend distinguishes React mounting in `main.tsx`, providers/existing page dispatch in `bootstrap/`, sign-in screen assembly in `pages/sign-in.tsx`, existing wallet behavior in `wallet-auth/`, and generic presentation/helpers in `ui/`/`lib/`. Module extraction is mechanical: preserve SDK preload, CSP nonce setup, hook/effect ordering, existing mobile-approval navigation and supported interaction behavior. Domains cannot import pages/bootstrap; generic UI/helpers cannot import domains or composition, including type-only/public-interface paths. No new routing library, consent/owner-management screen or frontend Discovery feature is added. Future `authorization/`/`applications/` roles remain documented without empty scaffolding.
- AC-11: The target skeleton, mapping, placement guidance and migrated executable ownership declaration use the explicitly named frontend/backend responsibilities consistently. There is no production catch-all `app/`, `features/` or obsolete `frontend/src/shared/ui/` destination, and no advice to create `src/app/` or `server/features/`. Logical checker roles remain composition/domain/shared classifications and do not dictate directory names. Every added production directory has an identifiable responsibility and owner. Current legacy paths and historical evidence are labeled as such; the dedicated existing `tests/app/` location is preserved rather than renamed by blanket text replacement.

## Out of scope

- Changing US-001-02's approved ACs, moving code as part of that story, bypassing existing host protection or delivering two stories concurrently.
- New wallet/authentication/OIDC features, new APIs, security-policy changes, visual redesign, new external services or universal-wallet claims.
- Refactoring the main authentication controller or state model, rewriting business logic, removing legacy dependency violations or expanding domain interfaces beyond necessary import/placement adjustments. Mechanical module extraction for the explicitly selected mounting/page/bootstrap responsibilities is allowed; behavioral redesign is not.
- Separate packages, npm workspaces, separate deployment pipelines, framework/build-tool migration, package upgrades or unnecessary lockfile churn.
- Moving/deleting runtime data, credentials, generated artifacts or historical evidence; altering human approvals; production release or host-permission changes.

## Dependencies and risks

- Human-selected names and a separate migration are settled. This full story and its final exact move/write scope still need human review and the normal READY gate.
- `docs/PROJECT_STRUCTURE.md`, Product Contract P7, PROCESS and relevant UI contract requirements apply. No human-owned product outcomes are changed.

Inventory actual files during delivery; do not use blind global replacement that modifies historical evidence or unrelated dependency fixtures.

- Trusted baseline/configuration updates must not self-authorize new exceptions. Initial host/bootstrap limitations in US-001-02 remain separate blockers, not waived by this migration.
- This DRAFT and its future-layout additions to the map/guide are separate shaping changes. Do not sweep them into US-001-02's source proposal merely because files share a working tree; preserve reviewable story-specific diffs before publishing either change.
