# US-004 — Manage only my applications using tokens

## User story

As an application owner, I want to use authorized management tokens to update and disable my applications, so that I can maintain integrations and stop new access when an application is retired.

## Story map context

- Journey/activity: [owner maintains applications](STORY_MAP.md#application-owner).
- Proposed release contribution: demonstrates ongoing owner control and isolation across applications and owners.
- Ordering/dependencies: US-002, US-001-07 and US-003. Deliver after US-003 supplies OIDC sign-in and renewable tokens; this story adds token-based management and disabled-client enforcement to the existing protocol flow.

## Acceptance criteria

Provisional outline; detail measurable boundaries and resolve policies before READY.

- AC-01: From the read-only owner list delivered by US-002, an authenticated owner edits an application's display name and registered redirect URIs, and sees changes persisted after a new sign-in.
- AC-02: A second owner cannot list, inspect, modify or disable the first owner's applications through either UI or direct API calls, including guessed client IDs. Unauthenticated access is denied.
- AC-03: Disabling an owned application persists its disabled state without altering another application. This story extends the US-003 flow to reject subsequent authorization and token issuance for disabled clients, including redemption of codes issued before disable and refresh-token issuance. Effects on already-issued access/refresh families require explicit policy before READY; US-003 does not silently settle disabling semantics.
- AC-04: Invalid configuration changes are rejected without partially overwriting the application's previous valid settings.

- AC-05 (provisional): Management requests require a valid token authorized for the intended management API, operation and wallet owner. Missing, invalid, expired or unauthorized tokens cannot modify client configuration. Token identity/type, issuance, audience, scopes, lifetime and revocation rules require human decisions before READY; neither an ID token nor possession of an ordinary third-party access token implicitly grants management authority.

## Out of scope

- Proposed: deletion, reactivation, ownership transfer, credential rotation and changes to scope/policy beyond the approved initial profile.
- Retroactive invalidation of already issued tokens unless separately approved; disabling must not be presented as that guarantee.

## Dependencies and risks

- US-002, US-001-07 and US-003; agree management-token policy, editable fields, disabled-client semantics, in-flight authorization handling and effects on existing tokens before READY.
- Full protocol enforcement of disable extends US-003 and must be verified in this story; management UI alone cannot prove it. Whether the existing UI switches to tokens, and whether registration/list/detail join the management-token boundary, remain open scope decisions. Accepted US-002 registration behavior is unchanged by this draft.
