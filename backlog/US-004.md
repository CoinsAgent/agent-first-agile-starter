# US-004 — Consent to standard application sign-in with my wallet

## User story

As an end user, I want to authenticate with my wallet and allow or deny an application's sign-in request, so that I control whether it receives my verified wallet identity.

## Story map context

- Journey/activity: [end user arrives, consents and returns](STORY_MAP.md#end-user).
- Proposed release contribution: connects authenticated wallet identity to standard third-party authorization and token issuance.
- Ordering/dependencies: US-001, US-002, US-003; map decision D5.

## Acceptance criteria

Provisional outline; detail protocol cases and resolve policies before READY.

- AC-01: For a valid registered application request, the user completes SIWE or reuses an eligible SIWE-origin session, sees the application identity/requested access, and can allow or deny. Denial returns the appropriate protocol error only to a validated redirect URI and issues no authorization code or tokens.
- AC-02: Under the proposed profile, approval returns a single-use authorization code; authenticated redemption with matching PKCE S256 produces standard OIDC tokens. The ID token's public sub is exactly the approved canonical verified address, identical across clients; client ID remains distinct. Issuer, audience, signature and nonce behavior can be validated by an independent relying party.
- AC-03: Discovery and verification keys support independent token verification. Claims never assert ownership/verification of an unrelated email or service account, including placeholder email values.
- AC-04: Invalid/unregistered redirects, unknown or disabled clients, disallowed scopes, missing/incorrect PKCE, invalid client authentication, wrong-client redemption, expired or replayed codes and inappropriate sessions issue no tokens. Invalid redirect requests never redirect sensitive data to untrusted locations. Disable is enforced for subsequent authorization and token issuance, including codes issued before disable.
- AC-05: Two applications can authorize the same wallet while maintaining independent credentials, redirect configuration and authorization boundaries. Session reuse never bypasses required consent or explicit standard reauthentication requests.

## Out of scope

- Proposed: refresh tokens, implicit flow, client_credentials, public/native clients, dynamic registration, remembered consent and extra identity claims.
- Unrelated account binding and agent identity.

## Dependencies and risks

- US-001–US-003; D5 client profile, consent policy, redirect rules, token/code validity, token validation behavior and supported OIDC request parameters must be detailed before READY.
- Framework capability for address-valued public subjects and SIWE-origin sessions is unverified. A supported extension must satisfy the contract; incompatibility is a gap to report, never permission to emit internal user IDs as sub.
- Existing-token revocation semantics require explicit product decisions; disabling must not promise retroactive invalidation by implication.
