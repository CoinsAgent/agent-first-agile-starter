## User story

As an application owner, I want to approve wallet authentication in a browser and then register, inspect, update and permanently delete my applications from a CLI using purpose-specific tokens, so that client operations do not depend on a Better Auth browser session.

## Story map context

- Journey/activity: [application owner](STORY_MAP.md#application-owner): CLI login → browser SIWE and approval → CLI management access → obtain an IAT → register → list/read/update/delete owned clients → revoke CLI access.
- Minimal usable outcome: wallet A registers two independent clients from the CLI, retains ownership across restart and browser logout, updates one and permanently deletes the other; wallet B cannot access either. Deletion stops server-authorized access and returns the client's quota slot.
- Dependencies: US-001/US-001-06 supply SIWE and canonical users; US-002 supplies registration validation/limits/credentials; US-001-07 supplies native ownership; US-003 supplies OIDC and third-party tokens. US-005 follows with the independent integration walkthrough.
- This targeted refinement replaces the former draft's web editing/disabling proposal. It proposes a CLI/token successor to accepted web registration/list behavior without rewriting earlier stories or granting implementation approval.

## Earlier repository decisions (historical baseline)

- All client operations are CLI-driven and token-authorized. A Better Auth cookie session alone cannot register, list, inspect, update or delete a client. Browser sessions remain relevant to SIWE authentication and approval, not as client API credentials.
- Registration requires an Initial Access Token (IAT). List/read/update/delete require a management access token. “CRUD” describes the complete capability; create has the explicit IAT boundary rather than accepting an ordinary management access token directly.
- Native ownership is `oauthClient.userId = user.id = canonical verified wallet address`, with `referenceId` null. Each client retains its distinct `client_id` and independent credentials.
- Owner authentication uses browser SIWE approval, after which the CLI uses tokens. The login protocol/bootstrap design remains open in D1 below.
- Management access tokens last at most 15 minutes, with no refresh token; after expiry the owner repeats browser approval. CLI logout revokes its management token.
- An IAT lasts at most five minutes and permits one successful registration. Its lifecycle must preserve safe retries without creating a second client or redisclosing a secret.
- Delete means permanent deletion. It prevents subsequent pending authorization completion, code redemption, refresh issuance and opaque access-token use for that client, and returns a slot within the existing 20-client-per-wallet limit. Already-issued signed ID tokens and application-owned sessions cannot be retracted.
- Existing web registration and application-list controls are replaced with CLI guidance. Preserve wallet sign-in and third-party authentication/consent.

These are the earlier recorded policies, retained for traceability. The shared discussion below revises the no-refresh model and requests a different ownership field and narrower target authorization. Where the sources conflict, the conflict is explicit; this section is not the current delivery contract. The story remains DRAFT with no READY decision or implementation authorization.

## Access-token subject analysis

`sub` identifies the subject represented by a token, not universally the owner of its OAuth client. For JWT access tokens, a user-delegated grant normally identifies its resource owner; a grant without a user, such as `client_credentials`, normally identifies the application. These are SHOULD requirements, and OAuth does not require JWT access tokens. See [RFC 9068 §2.2](https://www.rfc-editor.org/rfc/rfc9068.html#section-2.2).

For this story, **the approving wallet address is a reasonable management-token subject when the token represents that wallet's delegated management authority**. Validate token purpose, issuer, intended API, expiry, revocation and operation permission, then compare the authenticated subject to the target client's authoritative stored owner (`userId` in the accepted baseline; US-004 now selects immutable `referenceId` ownership, superseding that baseline for this story). Subject equality alone grants no authority. Wallet subject, calling CLI identity, target `client_id` and resource audience remain distinct.

If wallet B signs into an application owned by wallet A, the ordinary user subject remains B. Replacing it with A misidentifies the end user and violates the Product Contract. A future machine-only grant must not copy the application's owner into `sub` to manufacture wallet delegation; an owner attribute would need a separate, explicitly authorized meaning.

US-003's access tokens are opaque, without a client-readable JWT `sub`; the server resolves their user binding and UserInfo returns the wallet subject. Management tokens can likewise have a server-side wallet subject. No conversion of third-party access tokens to JWTs is proposed. The installed provider's JWT issuer uses `user.id` when a user is supplied, otherwise `client.clientId`, and protects the final `sub` from arbitrary custom-claim replacement. Source inspection is not a compatibility test.

An IAT authorizes registration; issuance, representation and validation policy are deployment-specific in [RFC 7591 §1.2 and §3](https://www.rfc-editor.org/rfc/rfc7591.html#section-1.2). Its authenticated owner binding must determine the authoritative stored owner (native `userId` in the accepted baseline; US-004 now selects immutable `referenceId` for its IAT registration). It is not an ID token or client secret.

Earlier recommendation, now narrowed by the shared discussion: a wallet-delegated management token permits approved operations across that wallet's clients, including IAT issuance. The current proposal additionally requires explicit target-client authorization; common wallet ownership alone is insufficient. This is an owner API. [RFC 7592 §1.2](https://www.rfc-editor.org/rfc/rfc7592.html#section-1.2) instead defines a registration access token associated with one registered client. Do not describe an owner-wide token as that credential or claim a custom owner API implements RFC 7592. The grill decisions below establish the selected management grant/consent boundary; the story still requires shared-understanding confirmation and an explicit READY decision.

## Current proposed outcome

The owner authorizes an approved public CLI through browser SIWE and Authorization Code + PKCE S256, without a distributed client secret. The CLI and an accompanying AI agent skill register through IATs and manage only explicitly authorized clients belonging to that wallet. Management uses opaque access tokens and rotating refresh credentials from the original user-authorized grant. Browser logout and explicit OAuth revocation have separate lifecycles. Multiple installations may share the approved public OAuth client identity while retaining separate credentials and revocation.

This incorporates the human selections visible in the shared discussion and subsequent grill. The explicit READY decision above authorizes delivery within the consolidated scope. Existing third-party confidential clients retain their approved protocol profile; adding the public management CLI must not broaden their permissions.

## Acceptance criteria

Reviewable DRAFT incorporating Q1–Q28. These criteria supersede conflicting earlier proposals for US-004 while preserving accepted story history. Individual design selections are not story READY approval.

- AC-01: CLI/browser approval — A first-time owner can initiate CLI login before registering a third-party application. The approved public CLI uses external-browser Authorization Code + PKCE S256 without a client secret. Show the requesting CLI, wallet, requested operations and target clients before explicit approval. Reject denial, cancellation, expired/replayed continuation, wrong verifier/state/wallet and substituted return targets. Never export wallet keys or browser cookies. Use loopback callbacks locally and documented SSH port forwarding for remote Linux; exclude Device Authorization and hosted callback relays. Reuse only unexpired SIWE-proven sessions under the existing policy, with explicit approval for each new or expanded delegation. Expired sessions require fresh SIWE. Explicit environment initialization provisions one deployment-owned public CLI identity as system configuration, outside wallet quotas and owner client CRUD. This is the approved bootstrap exception to IAT registration for wallet-owned applications; it uses neither a user session nor a distributed secret. CLI authorization continuations expire after five minutes, support cancellation and complete once; expiry requires a new attempt, and SIWE session reuse cannot extend that deadline.
- AC-02: Eligibility and authority — Only explicitly approved management OAuth client identities can obtain management permissions. Validate token activity, issuer, management resource/audience binding, original user-authorized grant, authenticated wallet, calling OAuth client and permitted operation/target. Ordinary RP access tokens, ID tokens, IATs, client secrets, client-credentials grants and cookie sessions cannot substitute. Client registration cannot self-grant management eligibility; a cookie accompanying invalid/missing bearer credentials cannot bypass validation. An allowlisted public client ID does not authenticate the executable.
- AC-03: Renewable independent authorization — Issue opaque management access tokens with a 15-minute maximum lifetime, rejecting at/after expiry and after effective revocation. Refresh authorization expires after seven days of inactivity or 30 days from original consent, whichever comes first; refresh cannot extend the absolute deadline. Only successful refresh or an authorized management operation resets inactivity; failed requests, page visits and token inspection do not count. With explicit offline consent, rotate refresh credentials from the Authorization Code-originated grant, retaining the owner and never expanding operation or target authorization. Browser logout/session expiry must not terminate the independently authorized grant; validate actual provider session bindings. CLI logout explicitly revokes the selected authorization and clears local credentials. Invalid/revoked/expired refresh authorization requires human reauthorization; missing permission requires new explicit consent. Provide a SIWE-owner browser page listing CLI authorizations and allowing individual revocation; revoking one stops its access and refresh credentials without revoking another installation. Refresh uses strict rotation without a replay grace window. Reusing a consumed refresh credential invalidates only its authorization and requires human reauthorization, including when its replacement response was lost; other installations remain valid. Browser authorization records show an owner-chosen descriptive label, unique authorization ID, creation time, last activity, expiry and granted permissions, without new IP tracking or device fingerprinting. If logout cannot confirm server-side revocation, report it incomplete and retain protected credentials for retry; explain browser revocation and never claim revocation succeeded. Clear local credentials only after confirmed logout revocation. When expanding permissions, issue replacement credentials only after explicit consent and revoke the selected old authorization as part of successful replacement; cancellation/failure preserves the original authorization and other installations remain unchanged. Restart preserves authorization deadlines/revocation.
- AC-04: IAT lifecycle — Only separately consented registration permission can obtain a five-minute IAT bound to the verified wallet and registration purpose, usable for one successful creation. Invalid metadata creates no client and does not count as successful use. Invalid, expired, revoked, forged, wrong-purpose or consumed IATs cannot create another client. An IAT cannot perform management, mint another IAT or act as client credentials. Preserve durable single-success enforcement. Revoking or expiring the parent authorization invalidates its outstanding IATs; clients already registered remain. Limit IAT issuance attempts to five per wallet per fixed minute across all authorizations, separately from registration limits; new authorizations never reset counters. A valid parent authorization with registration permission may reconcile the same committed submission’s public result after IAT consumption/expiry; it cannot create again or redisclose the secret. Changed submission metadata conflicts. Missing/revoked/expired parent authority cannot reconcile.
- AC-05: Immutable verified ownership — Derive ownership only from the validated IAT wallet, using lowercase `0x` plus 40 hex characters. Reject unverified binding and caller-supplied ownership/client-ID overrides. Assign ownership atomically; never expose an unowned client and repair it afterward. Two registrations produce distinct independent clients. No management route can transfer ownership. For this story, immutable `oauthClient.referenceId` is the sole authoritative client owner and equals the IAT-verified wallet. `user.id` remains the canonical verified wallet identity. This explicitly supersedes US-001-07’s client-owner representation for US-004; the human selects deployment to a new environment and new database, without converting/resetting existing storage. Reject incompatible storage without mutation. No client can register using a user session. Deployment execution remains a later explicitly scoped action after story delivery gates.
- AC-06: Registration integrity — Preserve existing confidential-web metadata validation, HTTPS non-loopback redirects, hashed secrets and one-time plaintext delivery; five-attempt fixed one-minute per-wallet windows including invalid attempts; owner-bound submission idempotency/conflicts; and the 20-current-client cap. Tokens/IATs do not reset limits. Deletion frees a slot. Lost-response reconciliation cannot duplicate registration, redisclose a secret or resurrect a deleted client. Changed retry metadata conflicts. Newly created clients require explicit browser consent before ongoing management permissions are added. The creation response may return the result and one-time secret; it does not silently grant subsequent management authority. If the one-time plaintext secret response is lost, disclose that it is unrecoverable; recovery requires consent to delete the client and register a replacement, not secret redisclosure.
- AC-07: Target and owner isolation — List/detail return only clients both owned by the authenticated wallet and explicitly authorized for read by this grant. A grant for client X cannot read, update or delete same-owner client Y without consent for Y; a multi-client grant can operate on its approved set within its operation permissions. Wallet B cannot access A's clients, including guessed IDs. Denials disclose no private existence/configuration/credential/submission information. Lists never return previous secrets. CLI parameters and local profile metadata grant no authority. Permissions are per-client operation sets: read X plus update Y never implies update X or read Y. Refresh preserves that exact mapping; expansion requires explicit owner consent. The SIWE-authenticated owner selects owned client names/IDs and per-client operations on the browser consent page. This is consent-only discovery, not session-authorized client CRUD; the CLI sees only its resulting authorized selection. Update/delete permissions do not imply read permission: without read, return only the selected client ID and operation outcome, never stored configuration.
- AC-08: Atomic update — The authorized owner can update display name and the complete redirect set, with persistence after restart. Reject invalid/unauthorized updates without partial changes. Client ID, owner, credential, grant capability and management eligibility remain immutable through editable metadata. New authorizations use the updated redirect set. Removing a redirect rejects pending authorization and code redemption using that redirect; already-issued token families retain their existing lifecycle.
- AC-09: Permanent deletion — Require confirmation for the selected authorized client. Atomically remove its registration/dependent server authorization state, free its quota slot and preserve unrelated users/clients/grants. After commit, pending authorization, code redemption, refresh issuance and opaque UserInfo access for the deleted client fail. Issuance/deletion cannot leave usable server-authorized tokens afterward. Use the same “not found or not authorized” result for nonexistent, already-deleted and unauthorized targets; a failed lookup changes nothing and the CLI cannot claim a deletion occurred; retries cannot resurrect clients and replacements get new IDs. Do not claim to retract signed ID tokens or application sessions. Deleting a target must not expand the grant to another client.
- AC-10: Server/web transition — Enforce IAT registration and token-only management on every exposed route/provider alias. Replace web registration/list controls with accurate CLI guidance and understandable old-link handling. Add a browser list and individual revoke controls for the wallet’s CLI authorizations; this is not a replacement web client CRUD interface. Preserve wallet/QR/RP authentication and consent. Changed browser approval, target selection, pending, denial and error states must meet the UI Design Contract: keyboard/focus/status behavior, actual contrast, 200% zoom, narrow viewports, light/dark themes and reduced motion.
- AC-11: CLI and AI skill — Document runnable login, IAT/create, list/get/update/delete and logout commands, stable exit codes and structured output. Include an AI agent skill that invokes those commands, explains human authorization/reauthorization and observes granted boundaries. Keep wallet keys, tokens and newly issued client secrets out of model prompts, command-line arguments/history and routine logs; explicit user-requested secret export must be handled by the CLI. Require interactive deletion confirmation or an explicit noninteractive confirmation option. Document secure credential storage and independent credential profiles under the shared public client identity. Support Linux desktop and Linux/SSH agents using the repository Node runtime, without registry publication; macOS/Windows are deferred. Use loopback locally and documented SSH forwarding remotely. Store credentials outside the repository in a private per-user directory with files accessible only to that OS user; reject unsafe permissions. Document same-user process access and do not claim encrypted storage or protection against host-account compromise. Ship a repository-local AI agent skill with documented, user-directed installation and CLI usage; no automatic installation into external agent environments. Retain one approved public OAuth client with independent credentials and revocation per authorization. No executable attestation or mandatory DPoP is required in this slice; credential theft is addressed through expiry and explicit revocation.
- AC-12: Actual verification — During approved delivery, exercise real provider/SQLite, CLI/browser approval and the agent skill commands. Cover wallet/target/operation isolation; management-client eligibility; PKCE/state/redirect rejection; public-client exchange without secrets; refresh rotation, no permission widening, browser logout, explicit revocation, expiry boundaries and restart; IAT retry integrity; immutable ownership; atomic update; permanent deletion and quota recovery; and independent credentials/revocation under one public client. Preserve wallet/QR/RP regressions and run full `bash scripts/verify.sh`. Record actual commands, tested revision, review and limitations in `work/US-004/evidence.md`; shared-chat claims and draft checks are not passing compatibility tests.
