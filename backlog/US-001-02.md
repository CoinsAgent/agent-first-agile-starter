# US-001-02 — Keep Codex changes within a clear project structure

## User story

As a human maintaining software developed with Codex, I want a clear, configurable directory ownership guide and a declared change boundary for each approved story, so that Codex knows where to add files or update code and unrelated areas remain under my control as the project grows.

## Story map context

- Journey/activity: [maintainer and Codex controlled-change journey](STORY_MAP.md#maintainer-and-codex).
- Proposed release contribution: one reusable harness slice spanning human story approval → baseline checks → proposed paths and implementation on a branch → final checks and human review → authorized merge. It supports the WalletGate evaluation release without adding authentication or OIDC behavior.
- Ordering/dependencies: requested after the structure-management interview. The suffix does not inherit another story's approval. Respect the existing one-story delivery limit; resolve the current delivery gate before starting this story.
- Product alignment: supports Product Contract P7 maintainability. This is starter/harness work, not an expansion of WalletGate's product outcomes. The human separately requested context-document updates for structure guidance; those changes do not authorize altering the Vision, identity/authentication policies or other product outcomes.

## Current workflow revision — human decision, 2026-11-07

The human explicitly requested: story approval → Codex checks → proposed allowed files on a new branch → human review of finished changes → merge to main, with business acceptance separate. This replaces the earlier two-stage PR scope-approval design and its independent App publisher requirement. Step 2 means baseline checks; step 3 includes implementation and final checks before step 4. See [PROCESS](../docs/PROCESS.md#approved-delivery-workflow).

Deliver configurable ownership/placement guidance, narrow branch scope and executable scope/dependency checks without relocating application code or adding authentication/OIDC behavior. Codex records technical path revisions within the approved story; changes to outcomes, security/privacy, cost, permissions or destructive actions still require a human decision.

## Acceptance criteria — revised by the explicit human process decision

- AC-01: A maintainer can inspect one documented project structure declaration and determine the responsibilities and allowed dependency directions of application entry points, frontend features, backend features/API endpoints, reusable UI, shared helpers/contracts, assets, tests, scripts, configuration and delivery artifacts. Every current tracked project area has an explicit responsibility or documented legacy classification; generated output, dependencies and runtime data are identified as non-source areas. Frontend API callers are distinguished from backend endpoints. The guide gives concrete placement examples for a new feature component, a feature helper, an endpoint, reusable UI and their tests; new feature-specific code stays with its feature and shared placement requires an actual reuse rationale.
- AC-02: The same convention/checking interface works with this repository's declared layout and a fixture with different frontend/backend/feature/shared paths. Invalid, overlapping or ambiguous ownership rules fail with actionable diagnostics rather than silently granting broad access. Adding a new top-level source area or changing ownership must be declared in the branch scope and presented in the finished human review; changes to approved outcomes require a prior human decision. No application file relocation or new product functionality is necessary to adopt the convention.
- AC-03: After human story approval, Codex runs baseline checks, creates a new story branch and proposes narrow allowed paths and reasons in its plan/scope manifest before implementation. Include tests, shared/config files and execution artifacts. No separate human file-scope approval is required. Record technical path revisions before affected edits; obtain a human decision when approved outcomes or other human-owned boundaries would change.
- AC-04: Within an approved scope, additions, edits, removals and renames pass the scope check. A new file under an approved feature directory is allowed; the same file outside it fails. Moving/renaming a file requires both source and destination paths to be allowed. The check evaluates the complete task/PR diff against a documented base, not just the last commit or current uncommitted changes. It handles filenames containing spaces, nested paths and deleted files without skipping them; path traversal or path normalization tricks cannot widen the allowed set. Missing base/scope/configuration inputs fail closed with a reason.
- AC-05: No always-writable common-file exemption exists. Shared UI/helpers/contracts, manifests, lockfiles, build configuration, migrations, entry points, tests, story records and execution artifacts require declared paths when needed. Codex records technical revisions and reasons within the approved story, avoids unrelated edits and presents proposed versus actual paths for final review. Negative coverage demonstrates that an edit outside declared paths fails even when product tests pass.
- AC-06: Cross-feature dependencies can use only the owning feature's declared public interface; direct imports of its private files fail with importer and target diagnostics. Features may depend on shared modules, but shared modules cannot depend on any feature, including its public interface, or on application composition. Product-specific assembly belongs in the application composition area, which consumes feature public interfaces and shared building blocks. Cover both frontend and backend features in this repository, permitted same-feature imports, permitted public-interface imports, permitted feature-to-shared imports, forbidden private imports and forbidden shared-to-feature/application dependencies. Exercise value imports, type-only imports and relevant alias/re-export bypasses, including a shared barrel that indirectly imports a feature. Frontend imports cannot pull in server-only code even through a public interface. Supported static-import forms, module resolution, exclusions and dynamic-import limitations are documented; unsupported configured source types are reported rather than described as checked. Existing violations may use only the finite baseline defined by AC-07.
- AC-07: Gradual adoption uses a finite, reviewable baseline identifying existing dependency violations precisely. An unchanged baselined violation does not block adoption; a new importer/target violation fails. Removing a violation succeeds without requiring it to return. A wildcard exemption, silently regenerated baseline or unexplained baseline addition cannot authorize a new violation. Any proposed baseline change is explicitly documented and presented for human review; checks must not be weakened merely to pass. Approved task file scope applies immediately and has no legacy exemption.
- AC-08: Final human review includes the complete branch diff and any changes to the scope manifest, ownership/interfaces, baseline, verification code, CI and instructions. Ordinary out-of-scope changes fail path checks, but candidate-edited enforcement is not claimed to provide independent tamper resistance. No custom GitHub App, independent trusted publisher, authenticated pre-edit scope comment or repository/PR digest authorization is required. Document this reliance on agent discipline and human review; retain legacy authorization tooling only as optional diagnostics, not a delivery gate. Candidate code receives no privileged write credentials or secrets.
- AC-09: Guidance explains story approval, baseline checks, proposed paths and implementation on a new branch, technical path revisions, final checks, human review of finished changes and authorized merge. Errors identify offending paths/dependencies and the next action. Codex does not hide unrelated edits, weaken checks to pass, fabricate approvals or silently change approved outcomes. No competing story-status files are introduced.
- AC-10: Scope/dependency checks integrate with the default verification workflow while preserving existing harness and product verification. Reproducible positive, negative, boundary and policy-change fixtures exercise the applicable revised AC-01–AC-09; both layouts are tested. Evidence records actual commands/results, checked diff base and head, supported analysis coverage, baseline entries and unresolved limitations. A successful check alone does not imply human acceptance or that local writes were prevented.
- AC-11: Present finished branch changes and passing verification evidence for explicit human review before merge. The reviewed commit is identified; subsequent changes are checked and presented again. A PR is optional in the process but required when existing host protection demands one. Follow actual host rules and report mismatches without bypassing them; this revision does not authorize host-setting changes. Merge requires authorization and business acceptance remains separate. No independent App or separate pre-edit path approval is required. Missing required engineering checks still block QA_PASSED; pending human final approval is reported separately from technical QA.
- AC-12: The context documents consistently direct Codex to establish the documented skeleton before implementing a new area and to create directories only for approved real files. `docs/PROJECT_STRUCTURE.md` owns the skeleton, existing-path mapping, dependency directions and placement examples; `AGENTS.md` routes code work there; Product Contract P7 states maintainability intent; the UI contract distinguishes shared primitives, feature UI and app composition; PROCESS, shaping/delivery skills and the plan template require structure/scope planning. There is no competing directory tree or claimed executable enforcement in those references. A maintainer can trace the placement of a new feature component, endpoint, API caller, shared UI change and test from the guide to proposed task paths without creating empty roadmap directories or relocating existing files.
