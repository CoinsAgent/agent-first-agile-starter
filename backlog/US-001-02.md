# US-001-02 — Keep Codex changes within a clear project structure

## User story

As a human maintaining software developed with Codex, I want a clear, configurable directory ownership guide and a human-approved change boundary for each task, so that Codex knows where to add files or update code and unrelated areas remain under my control as the project grows.

## Story map context

- Journey/activity: [maintainer and Codex controlled-change journey](STORY_MAP.md#maintainer-and-codex).
- Proposed release contribution: one reusable harness slice spanning project orientation → proposed file scope → human approval → scoped editing → automated verification → protected human review. It supports the WalletGate evaluation release without adding authentication or OIDC behavior.
- Ordering/dependencies: requested after the structure-management interview. The suffix does not inherit another story's approval. Respect the existing one-story delivery limit; resolve the current delivery gate before starting this story.
- Product alignment: supports Product Contract P7 maintainability. This is starter/harness work, not an expansion of WalletGate's product outcomes. The human separately requested context-document updates for structure guidance; those changes do not authorize altering the Vision, identity/authentication policies or other product outcomes.

## Proposed minimal release and scope

Deliver a reusable convention, project-specific configuration, agent guidance, executable checks and protected-review setup instructions as one usable workflow. Configure this repository's current layout as the first example without moving application files. A second small fixture with different directory names demonstrates that the convention is not tied to React, Express, WalletGate, or fixed `src/` and `server/` names. Supported import analysis must be explicit; declaring a different layout does not establish support for every language.

The existing story remains authoritative for status and ACs. Its execution plan records proposed writable paths and rationale; a machine-readable scope representation may accompany it for checking but is not a competing status or approval record. Human review authorizes an exact scope revision on one draft pull request (PR). Approval of story outcomes alone must not implicitly authorize all repository paths.

The human selected documentation-first skeleton planning: document and agree on the complete intended structure before implementing a new area, then create directories only as approved work needs real files. `docs/PROJECT_STRUCTURE.md` is the human-readable source of truth, distinguishing existing owners from proposed destinations; other context documents link to it rather than copying its tree. The explicitly requested documentation update supplies initial guidance now, but does not complete this story's executable checks, trusted authorization, baseline or host protection.

## Selected dependency direction and placement

- Application composition → feature public interfaces and shared building blocks. A product-specific header that displays wallet identity belongs in the application's composition area; it can assemble a generic header with a wallet feature's exported component. These are logical responsibilities mapped to project-configured paths, not mandatory directory names or a requirement to move existing files.
- Features → shared building blocks. For example, a wallet feature supplies `loading` and `onClick` to a reusable button; the button does not read wallet-authentication state itself. Feature-owned components and helpers remain inside their feature.
- Shared building blocks → other permitted shared building blocks, never features or application composition. This prohibits importing even a feature's public interface, including type-only imports and indirect dependencies through aliases or re-export barrels within the documented static-analysis coverage. Common contracts needed by multiple features belong in a suitable shared contract area; this does not authorize moving existing code without approved scope.
- Cross-feature use still goes through the owning feature's declared public interface and must respect frontend/backend runtime boundaries. A public server interface is not permission for frontend code to import server implementation. Existing violations follow the finite-baseline adoption rule; no new reverse dependency is allowed.

## Selected workflow — one PR, two review stages

1. After the story is READY, Codex prepares the plan and proposed writable paths on one draft PR. A PR is the review page for proposed changes before they enter the main branch. The trusted workflow narrowly identifies which planning/scope proposal files may be prepared before scope approval; this is not an implementation or common-file exemption. Include those files in the proposed scope so the eventual complete PR diff is covered.
2. The human reviews and explicitly approves the scope proposal, including necessary shared files, tests and delivery artifacts. The approval binds the repository, PR, reviewed commit, exact scope contents and applicable trusted policy revision. The technical representation is an implementation choice, but ordinary editable approval text is insufficient evidence. No implementation edits precede this approval.
3. Codex implements within that approved scope on the same PR. Subsequent implementation commits can reuse the recorded scope authorization only while the approved scope and governing policy remain unchanged. The authorization grants permission to edit paths; it is not final approval of the resulting code.
4. If more paths or policy changes become necessary, Codex pauses before the affected edits, explains the proposed revision on the same PR and obtains new explicit human approval. Existing edits remain reviewable; the proposed revision does not authorize itself.
5. Trusted checks verify the entire PR diff against the approved scope and feature boundaries. When implementation is complete, the human reviews the final changes with passing checks. Final merge approval must apply to the current head; new commits invalidate that final approval. A historical scope approval never substitutes for final review, even when the host dismisses an earlier review after a push.
6. Merge, story acceptance and release remain separate actions governed by PROCESS. This story does not automatically merge the PR, write human metadata or authorize a release.

## Acceptance criteria

- AC-01: A maintainer can inspect one documented project structure declaration and determine the responsibilities and allowed dependency directions of application entry points, frontend features, backend features/API endpoints, reusable UI, shared helpers/contracts, assets, tests, scripts, configuration and delivery artifacts. Every current tracked project area has an explicit responsibility or documented legacy classification; generated output, dependencies and runtime data are identified as non-source areas. Frontend API callers are distinguished from backend endpoints. The guide gives concrete placement examples for a new feature component, a feature helper, an endpoint, reusable UI and their tests; new feature-specific code stays with its feature and shared placement requires an actual reuse rationale.
- AC-02: The same convention/checking interface works with this repository's declared layout and a fixture with different frontend/backend/feature/shared paths. Invalid, overlapping or ambiguous ownership rules fail with actionable diagnostics rather than silently granting broad access. Adding a new top-level source area or changing ownership requires explicit human review. No application file relocation or new product functionality is necessary to adopt the convention.
- AC-03: On one draft PR, before implementation, Codex proposes narrow writable files/directories and rationale in the task plan, including required tests and plan/evidence updates. Only explicitly designated planning/scope proposal files may be prepared under the trusted pre-implementation procedure, and they must be included in the proposed scope; this cannot authorize application or checker edits. The human approves the exact proposed scope revision before any implementation edit. Missing approval or a changed proposal stops dependent work. The approved scope remains usable across implementation commits on that PR only while its contents and applicable trusted policy remain unchanged. Codex may inspect related code to understand dependencies; read access does not grant write access. Documentation explains that instructions and CI detect/control workflow and merging, not local filesystem write permissions.
- AC-04: Within an approved scope, additions, edits, removals and renames pass the scope check. A new file under an approved feature directory is allowed; the same file outside it fails. Moving/renaming a file requires both source and destination paths to be allowed. The check evaluates the complete task/PR diff against a documented base, not just the last commit or current uncommitted changes. It handles filenames containing spaces, nested paths and deleted files without skipping them; path traversal or path normalization tricks cannot widen the allowed set. Missing base/approval/configuration inputs fail closed with a reason.
- AC-05: No always-writable common-file exemption exists. Shared UI/helpers/contracts, dependency manifests, lockfiles, build configuration, database migrations, application entry points, tests, story records and execution artifacts require explicit inclusion when needed. If a change requires another path, Codex stops before editing it, explains the files and reason, obtains human approval of the revised scope, and then continues. Negative coverage demonstrates that an unrelated-file edit fails even when all product tests pass.
- AC-06: Cross-feature dependencies can use only the owning feature's declared public interface; direct imports of its private files fail with importer and target diagnostics. Features may depend on shared modules, but shared modules cannot depend on any feature, including its public interface, or on application composition. Product-specific assembly belongs in the application composition area, which consumes feature public interfaces and shared building blocks. Cover both frontend and backend features in this repository, permitted same-feature imports, permitted public-interface imports, permitted feature-to-shared imports, forbidden private imports and forbidden shared-to-feature/application dependencies. Exercise value imports, type-only imports and relevant alias/re-export bypasses, including a shared barrel that indirectly imports a feature. Frontend imports cannot pull in server-only code even through a public interface. Supported static-import forms, module resolution, exclusions and dynamic-import limitations are documented; unsupported configured source types are reported rather than described as checked. Existing violations may use only the finite baseline defined by AC-07.
- AC-07: Gradual adoption uses a finite, reviewable baseline identifying existing dependency violations precisely. An unchanged baselined violation does not block adoption; a new importer/target violation fails. Removing a violation succeeds without requiring it to return. A wildcard exemption, silently regenerated baseline or agent-written baseline addition cannot authorize a new violation. Approved task file scope applies immediately and has no legacy exemption.
- AC-08: A PR cannot authorize itself by expanding its scope, editing approval text, changing ownership/interfaces, adding baseline entries, weakening checks, editing CI, or changing these governance instructions. Verification uses a documented trusted policy/checker and authenticated human authorization bound to the repository, PR, reviewed commit, exact scope contents and applicable policy revision, independent of untrusted PR execution. Tests demonstrate that ordinary unauthorized changes and attempts to modify their own enforcement both remain blocked; copied authorization from another PR/repository, a changed scope after approval, or a changed governing policy cannot reuse the previous authorization. An unchanged approved scope can cover later implementation commits on the same PR. Local metadata alone is never treated as proof of human identity; untrusted PR code receives no write credentials or privileged execution. The initial installation and later policy updates have an explicit human-reviewed bootstrap/update procedure, rather than trusting the new rules merely because they appear in the PR.
- AC-09: Repository guidance and the delivery workflow explain orientation, file placement, initial scope approval, scoped execution, scope expansion, public feature interfaces, baseline maintenance and failure recovery. Errors name the offending paths/dependency and necessary next action. Codex does not solve a failing check by moving unrelated files into its allowed directory, widening globs, weakening rules, or silently changing an approved story. No new story-status files or agent-written human approval metadata are introduced.
- AC-10: Scope/dependency checks integrate with the default verification workflow while preserving existing harness and product verification. Reproducible positive, negative, boundary and tampering fixtures exercise AC-01–AC-09; both layouts are tested. Evidence records actual commands/results, checked diff base and head, supported analysis coverage, baseline entries and unresolved limitations. A successful check alone does not imply human acceptance or that local writes were prevented.
- AC-11: The same PR supports initial scope review and final implementation review. Protected-PR setup requires authenticated human final review and the trusted verification status before merging, with final approvals invalidated when new commits arrive. Retaining historical authorization for an unchanged scope must not preserve or simulate final merge approval. Tests distinguish valid prior scope approval with a pending final review from a currently merge-approved head; a stale review cannot authorize merging a new head. Governance paths also require human review. Documentation distinguishes committed workflow files from host settings, and records the actual hosting configuration/evidence when available. If permissions or hosting capabilities prevent enforcement, delivery reports that gate as blocked; local green tests are not evidence that protected merging is enabled. Changes to host permissions/settings require the human authorization required by repository rules.
- AC-12: The context documents consistently direct Codex to establish the documented skeleton before implementing a new area and to create directories only for approved real files. `docs/PROJECT_STRUCTURE.md` owns the skeleton, existing-path mapping, dependency directions and placement examples; `AGENTS.md` routes code work there; Product Contract P7 states maintainability intent; the UI contract distinguishes shared primitives, feature UI and app composition; PROCESS, shaping/delivery skills and the plan template require structure/scope planning. There is no competing directory tree or claimed executable enforcement in those references. A maintainer can trace the placement of a new feature component, endpoint, API caller, shared UI change and test from the guide to proposed task paths without creating empty roadmap directories or relocating existing files.
